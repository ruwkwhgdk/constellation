외부 제작 원본과 게임 자산 관리 R&D — 2026-10-10

결론
게임 실행용 자산과 편집 원본은 구분한다. 현재 확인한 소녀 런타임 코드는 Unreal 오브젝트 참조만 사용하며 외부 Blender/FBX/PNG 경로를 읽지 않는다. 외부 원본을 바꿔도 실행 중인 게임 메시가 자동으로 바뀌는 구조는 발견하지 못했다. 다만 에디터의 수동/자동 재임포트는 원본 변경을 .uasset에 반영하므로 제작 단계의 영향은 있다.

프로젝트에서 확인한 근거
- LittleGirlLocomotionComponent는 SkeletalMesh/BlendSpace 오브젝트를 참조한다. Source, SceneDirector 소스 및 Config 검색에서 Constellation_ArtWorkspace/ArtSource/Downloads 직접 접근 문자열이 없었다.
- production_asset_check.json의 메시·텍스처 19개 재임포트 원본은 프로젝트 내부 ArtSource/LittleGirl_Production/Source를 가리킨다. 애니메이션을 포함한 모든 종류의 커스텀 임포트 메타데이터 전수 검증을 뜻하지 않는다.
- 로컬 에디터 설정 bMonitorContentDirectories=True. 감시 디렉터리는 /Game/이며 외부 ArtWorkspace 및 프로젝트 ArtSource 감시 설정은 발견되지 않았다. 팀원의 에디터 설정은 다를 수 있다.
- Config에서 ArtSource를 추가 런타임 디렉터리로 스테이징하는 설정은 발견되지 않았다.
- 설치된 UE5.8 AssetImportData.h는 IsEditorOnly()=true이고 SourceData는 WITH_EDITORONLY_DATA에 들어 있다.
- 소녀 Source 24개 파일 약 103.4 MiB. 중간 Locomotion 약 81.2 MiB, Prototype/Textures 약 23 MiB. 다른 제작 원본과 중복 파일은 별도 추가 용량이다.
- 앞선 검증에서 빌드/쿠킹 성공. 원본을 완전히 제외한 새 체크아웃의 클린 쿠킹·패키지 플레이는 아직 수행하지 않았다. 따라서 모든 프로젝트 파일의 외부 의존성이 0이라고 단정하지 않는다.

실무 방식 비교
1. 단일 저장소 + Git LFS
   코드·엔진 자산·아트 원본을 같은 커밋으로 묶을 수 있다. 소규모 프로젝트에 단순하지만 반복 저장되는 대형 원본 때문에 LFS 저장량과 이력 관리 범위가 커진다. LFS는 분리 정책이나 자동 갱신 차단 기능이 아니라 대형 바이너리 저장 방식이다.
2. 게임 저장소 + 아트 원본 저장소
   게임 저장소는 Content/Source/Config/Plugins와 필요한 도구·문서, 아트 저장소는 .blend/.fbx/.glb/원본 텍스처·제작 스크립트·승인된 Export를 관리한다. 게임 체크아웃만으로 빌드가 가능해야 한다. 제작 원본을 편집할 때만 아트 저장소를 받는다. 어느 아트 버전에서 어느 엔진 자산이 생성됐는지 매니페스트가 필요하다.
3. Perforce/P4 + 자산 관리
   바이너리 잠금과 대형 자산 협업을 지원한다. 규모가 커지면 후보지만 현재 GitHub 프로젝트에 당장 도입하면 서버·권한·백업 운영 부담이 생긴다. 현재는 2번에 Git LFS를 적용하는 것을 권고한다.

권고 구조 (아직 적용/원격 생성하지 않음)
- 기존 ruwkwhgdk/constellation, develop: 실행에 필요한 .uasset/.umap, 코드, 설정, 검증 도구, 아트 버전 매니페스트.
- 별도 비공개 아트 저장소 후보 constellation-art-source, develop: LittleGirl 제작 원본, 중간 이력, 최종 Export, 텍스처, 제작 도구. 이번 커밋에 포함된 SchoolLocker/SchoolOpening 원본도 같은 기준으로 분리한다. 다른 채팅의 기존 전체 아트 이력을 일괄 이관하는 것은 별도 범위다.
- 아트 저장소는 필수 서브모듈로 두지 않는다. 게임 빌드가 아트 저장소 체크아웃을 요구하지 않게 한다.
- 매니페스트: 아트 저장소/커밋, 소스 상대 경로, Export SHA256, 대상 Unreal 자산, 툴 버전, 임포트 옵션, 검증 결과.
- 아트 원본은 자동 감시하지 않는다. 승인된 Export만 명시적인 재임포트 절차로 반영한다. 개인 절대 경로를 팀 계약으로 쓰지 않는다.
- 중요한 원본은 별도 백업도 유지한다. LFS 과거 버전은 계속 공간을 차지하므로 보존·잠금 정책을 둔다.

푸시 전 작업 순서
1. 아트 원본/게임 자산 분류 목록을 확인한다. 현재 로컬 393dbe9 및 9b17f71은 원본을 함께 담은 미푸시 커밋이므로 그대로 올리지 않는다.
2. 현재 작업과 원본을 보존한 뒤, 미푸시 두 커밋을 분리 구조에 맞춰 재구성한다. 나중에 삭제 커밋만 덧붙이면 앞선 커밋의 아트 이력도 원격에 올라가므로 충분하지 않다. 이미 원격에 있는 기존 이력은 건드리지 않는다.
3. 아트 원본 해시와 내보내기 매니페스트를 만들고, 재임포트 경로는 관리되는 Export 사본으로 연결한다. 원본 편집과 게임 반영을 명시적으로 구분한다.
4. 아트 원본 없는 격리된 게임 체크아웃에서 자산 로드·클린 쿠킹·기본 플레이를 검증한다. 경로 누락이 있으면 그때 수정한다.
5. 구체적 아트 원격 저장소와 업로드 범위를 확정한 뒤 게임/아트 각각 develop에 푸시한다.

현재 배포 상태
- 원격 푸시 없음. 로컬 develop 두 커밋만 생성됨.
- Git diff 검사 및 Git LFS 포인터 검사 통과.
- 자동 승인 검토는 원본을 GitHub origin으로 전송하는 구체적 승인이 부족하다는 이유로 기존 푸시 명령을 거절했다. 이후 사용자가 원본 의존성 R&D와 저장소 분리 검토를 요청하여 푸시를 보류했다.
- Notion 소녀 작업 기록은 작성됨. 모델/본편 적용은 완료로 기록하고 전용 연출 모션은 별도 후속 작업으로 분리했다. 저장소 정리는 별도 미완료 단계다.
