# PCG 기반 복도식 아파트 실내 진입 구조 구현 워크플로우 (UE 5.8)

이 문서는 앞선 문서(`terrain-detail-and-roads-workflow.md`)의 2.7절에서 "미해결 과제"로 남겨두었던
**PCG 아파트 자동생성**을 실제로 착수하는 문서다. 목표는 한국의 복도식 아파트 한 개 동을
PCG로 절차적으로 생성하되, 그래박스가 아니라 **플레이어 캐릭터가 실제로 현관을 지나 복도와
세대 내부까지 걸어 들어갈 수 있는 콜리전·내비게이션 구조**로 만드는 것이다.

**이번 라운드에서 확정한 범위** (질문/답변 기준):

- PCG 적용 범위: 건물 구조체(바닥·벽·천장·계단실·난간)와 반복 소품(격벽, 문틀 등) **모두** 절차적 생성
- 규모: **단일 동 프로토타입** (여러 동 확장은 8장에 로드맵만 남김)
- 에셋: **블록아웃 프리미티브만 사용** (`/Engine/BasicShapes/Cube`, `Plane`, `Cylinder`) — 모듈러 에셋 확보 전 단계

---

## 0. 작업 순서 요약

1. 복도식 아파트의 실제 구조(편복도/중복도, 세대수, 코어 위치)를 게임용 치수로 정의한다.
2. 층수·세대수·복도폭 등을 PCG Graph의 **User Parameters**로 노출해 데이터 기반으로 설계한다.
3. `MainGraph → SG_Floor(층 반복) → SG_UnitRow(세대 반복)` 3단 그래프 계층을 구성한다.
4. 층 반복과 세대 반복 각각에 **Attribute Partition + Loop Subgraph** 패턴을 적용한다.
5. 벽에 문 폭만큼 개구부를 남기고, 편복도 오픈사이드에는 난간(파라펫)을 배치한다.
6. Nav Mesh Bounds Volume과 Generation Trigger를 설정해 실제로 걸어 다닐 수 있는지 검증한다.

---

## 1. 복도식 아파트 구조 정의 (게임용 치수로 변환)

### 1.1 편복도 vs 중복도

한국 아파트는 크게 계단식(홀식)과 복도식으로 나뉘고, 복도식은 다시 편복도/중복도로 나뉜다.

| 구분 | 계단식 | 복도식(편복도) | 복도식(중복도) |
|---|---|---|---|
| 층당 세대수 | 2~4가구 | 6~12가구 | 6~12가구 |
| 공용 복도 | 없음/최소 | 한쪽에 개방형 복도 (호텔 구조) | 건물 중앙에 폐쇄형 복도, 양쪽에 세대 |
| 통풍·채광 | 대부분 양쪽 확보 | 복도 반대쪽만 채광, 복도 쪽은 창 제한 | 중간 세대는 편측 채광만 가능 |
| 코어(계단실/EV) | 세대별 소규모 코어 반복 | 중앙 1개 코어에서 좌우로 복도 연장 | 중앙 코어 + 중복도 |

**이 프로토타입은 편복도 방식을 기본값으로 채택한다.** 이유는 두 가지다.

- 옛 5층 주공아파트류의 "한국 복도식 아파트"의 전형적 이미지에 가장 가깝다.
- 구조적으로 한쪽 면(개구부/난간)만 처리하면 되므로 첫 블록아웃 난이도가 낮다.

중복도는 5장에서 `CorridorType` 파라미터로 분기하는 방법만 짧게 언급해두고, 실제 구현은 편복도를
기준으로 서술한다.

### 1.2 기준 치수 (파라미터 기본값)

실제 건축 자료에서 확인한 범위를 게임 플레이에 무리 없는 값으로 반올림했다.

| 항목 | 실제 범위 | 이 프로젝트 기본값 |
|---|---|---|
| 층고(바닥-바닥) | 약 2.8~3.0m | **300cm** |
| 층당 세대수(편복도) | 6~12가구 | **6가구** (코어 기준 좌우 3가구씩) |
| 세대 정면 폭 | 약 6~9m | **700cm** |
| 복도 폭 | 최소 1.2m, 통상 1.5~1.8m | **180cm** |
| 코어(계단실+EV) 폭 | 약 4~6m | **500cm** |
| 현관문 폭 | 표준 90~100cm | **100cm** |
| 벽 두께 | — | **20cm** |
| 편복도 난간(파라펫) 높이 | 실무적으로 허리~가슴 높이 | **110cm** |

이 치수들은 "정답"이 아니라 PCG 그래프의 입력 파라미터이므로, 나중에 숫자만 바꿔서 다른 평면을
바로 뽑아볼 수 있다는 점이 핵심이다.

## 2. 데이터 기반 파라미터 설계 (User Parameters)

UE 5.8 PCG 그래프는 Graph 애셋의 **Details 패널 → User Parameters** 탭에서 파라미터를 정의하면,
레벨에 배치한 PCG Graph Instance(또는 PCG Component)의 Details 패널에 그대로 노출되어 인스턴스별로
값을 다르게 줄 수 있다. 도로 문서에서 Landscape Edit Layer로 비파괴 편집 구조를 만들었던 것과
같은 철학이다 — "그래프를 다시 짜지 않고 숫자만 바꿔 여러 변형을 뽑는다."

정의할 파라미터:

- `FloorCount` (int) = 5
- `FloorHeight` (float, cm) = 300
- `UnitsPerSide` (int) = 3 — 코어 기준 한쪽 방향 세대수 (양쪽 합쳐 층당 6세대)
- `UnitWidth` (float, cm) = 700
- `UnitDepth` (float, cm) = 800 — 세대 내부 블록아웃 깊이(프로토타입용 단일 룸)
- `CorridorWidth` (float, cm) = 180
- `CoreWidth` (float, cm) = 500
- `DoorWidth` (float, cm) = 100
- `WallThickness` (float, cm) = 20
- `ParapetHeight` (float, cm) = 110
- `CorridorType` (enum: `SingleLoaded` / `DoubleLoaded`, 기본값 `SingleLoaded`)

## 3. 그래프 계층 구조

```
MainGraph
 └─ (Create Points Grid: Z축 1D, count=FloorCount, spacing=FloorHeight)
     └─ Attribute Partition (Index) → Loop Subgraph: SG_Floor
         ├─ 코어 블록아웃 (계단실/EV 매스, 층마다 동일 위치 반복)
         └─ (Create Points Grid: X축 1D, count=UnitsPerSide, spacing=UnitWidth) ×2 (좌/우, Transform Points로 미러링)
             └─ Attribute Partition (Index) → Loop Subgraph: SG_UnitRow
                 ├─ 바닥/천장 슬래브 (Static Mesh Spawner: Cube)
                 ├─ 세대 간 격벽 (Static Mesh Spawner: Cube, 얇고 김)
                 ├─ 복도측 외벽 + 현관 개구부 (2세그먼트 벽 + 문틀)
                 ├─ 오픈사이드 파라펫(편복도 난간)
                 └─ 세대 내부 블록아웃 룸(바닥/3벽/천장, UnitDepth만큼)
```

Loop Subgraph는 반드시 **파티션된 데이터**를 받아야 한 포인트씩 개별 처리된다. 공식 포럼에서
확인한 필수 절차는 다음과 같다.

1. 각 포인트에 인덱스 속성을 만든다 (Copy Attribute로 `$Index` → `Index` 속성 복사, 또는
   Create Attribute + Attribute Noise 없이 순서값 그대로 사용).
2. **Attribute Partition** 노드에 그 `Index` 속성을 지정해 포인트 하나당 하나의 파티션(subset)이
   되도록 나눈다.
3. 파티션된 데이터를 **Loop Subgraph** 입력에 연결한다.
4. 서브그래프 내부에서는 그 파티션(=포인트 1개)만 들어오므로, Attribute Select 등으로 그 포인트의
   속성(층 인덱스, 세대 인덱스 등)을 꺼내 위치·크기 계산에 사용한다.

이 패턴을 `MainGraph → SG_Floor`와 `SG_Floor → SG_UnitRow` 두 곳 모두에 동일하게 적용한다.
원본 포인트 데이터를 그대로 Loop Subgraph에 꽂으면 파티션 없이 전체가 하나로 처리되어
"층마다 다른 위치에 배치"가 되지 않는 실수를 가장 많이 한다.

---

## 4. MainGraph: 층 반복 만들기

1. **Create Points Grid**로 Z축 방향 1×1×`FloorCount` 그리드, 간격 `(0,0,FloorHeight)`를 생성한다.
   각 포인트가 "층 원점"이 된다.
2. 포인트 인덱스를 `FloorIndex` 속성으로 복사한다.
3. `FloorIndex` 기준 **Attribute Partition** → **Loop Subgraph(SG_Floor)** 로 연결한다.
4. 각 층 서브그래프의 출력(바닥/벽/난간/유닛 등 모든 Static Mesh 스폰 데이터)을 **Merge**해서
   최종 출력으로 내보낸다. 실제 스폰(Static Mesh Spawner)은 하위 서브그래프 안에서 이미
   끝나 있으므로, MainGraph 레벨의 Merge는 디버그·통계용으로만 써도 무방하다.

## 5. SG_Floor: 코어 + 좌우 복도 + 세대열

### 5.1 코어(계단실/엘리베이터) 블록아웃

코어는 매 층 동일한 로컬 좌표에 반복되므로 절차적으로 "변형"할 필요가 크지 않다. 층 서브그래프
입력으로 받은 층 원점(Point, Z=현재 층 높이)을 기준으로 **Static Mesh Spawner**로 다음을
고정 오프셋에 배치한다.

- 계단실 매스 박스 1개 (`CoreWidth` × 계단실 깊이, 층고만큼 세움 — 실제 계단 단은 프로토타입에서 생략하고 경사로 형태의 Ramp 큐브로 대체해도 됨)
- 엘리베이터 샤프트 매스 박스 1개
- 코어 전실 바닥 슬래브

이 부분은 "층마다 반복"만 되면 되므로 SG_Floor 안에서 Loop 없이 바로 Static Mesh Spawner
3~4개를 병렬로 연결하면 된다.

### 5.2 좌우 복도 세대열 만들기

편복도는 실제로 "코어를 중심으로 좌우로 복도가 뻗어나가는" 배치가 많으므로, 코어 좌/우 각각에
`Create Points Grid`(X축 1D, count=`UnitsPerSide`, spacing=`UnitWidth`, 시작 오프셋 =
`CoreWidth/2 + UnitWidth/2`)를 하나씩 만든다. 오른쪽은 그대로, 왼쪽은 **Transform Points**로
X축을 미러링(스케일 -1 또는 Rotate 180°)해서 같은 그래프를 재사용한다. 즉 세대 생성 로직
(SG_UnitRow)은 한 번만 만들고, 좌/우는 입력 포인트의 위치·방향만 다르게 넣는다.

각 포인트에 `UnitIndex` 속성을 부여하고, `UnitIndex` 기준 Attribute Partition → Loop
Subgraph(SG_UnitRow)로 연결한다.

### 5.3 `CorridorType` 분기 (중복도 확장 여지만 남겨둠)

`CorridorType == DoubleLoaded`일 때는 반대쪽에도 동일한 세대열을 하나 더 생성하면 된다.
Attribute Filter로 `CorridorType` 값을 검사해 두 번째 세대열 브랜치를 켜고 끄는 정도로 충분하다.
이번 프로토타입에서는 `SingleLoaded`만 실제로 검증한다.

## 6. SG_UnitRow: 세대 하나 = 벽 + 개구부 + 파라펫 + 실내 블록아웃

이 서브그래프에 들어오는 것은 세대 1개의 원점 포인트(코어 기준 상대 위치, 층 원점 Z 포함)다.

### 6.1 바닥/천장 슬래브

`Static Mesh Spawner`(Cube)를 `UnitWidth × (CorridorWidth + UnitDepth) × 슬래브두께` 크기로
스케일해서 배치한다. **복도 바닥과 세대 바닥을 하나의 연속된 슬래브로 이어 붙여서 문턱 단차가
생기지 않게 한다** — 단차가 있으면 Character Movement의 Max Step Height(기본 약 45cm)를
초과하는 경우 캐릭터가 걸려서 못 지나가므로, 프로토타입 단계에서는 아예 단차를 0으로 둔다.

### 6.2 세대 간 격벽

세대 경계(양 옆)에 얇고 긴 `Static Mesh Spawner`(Cube, 두께=`WallThickness`, 높이=`FloorHeight`)를
배치한다. 좌우 이웃 세대와 격벽을 공유하므로 중복 스폰을 피하려면 "오른쪽 경계만 자기 책임으로
스폰"하는 규칙을 정해두면 편하다 (Attribute Filter로 `UnitIndex`의 짝/홀만 스폰하는 방식도 가능).

### 6.3 복도측 외벽 + 현관 개구부 (블록아웃 프리미티브로 "문" 만들기)

모듈러 문 메쉬가 없는 상태에서 개구부를 만드는 실무적인 방법은 벽 자체를 boolean으로 뚫는 것이
아니라, **벽을 문 폭만큼 미리 나눠서 배치**하는 것이다.

1. 세대 폭(`UnitWidth`)에서 `DoorWidth`를 뺀 나머지를 절반씩 좌우 벽 세그먼트로 계산한다:
   `SegmentWidth = (UnitWidth - DoorWidth) / 2`.
2. 벽 세그먼트 포인트 2개(좌/우)를 생성해 각각 `Static Mesh Spawner`(Cube, 폭=`SegmentWidth`)로
   스폰한다. 가운데 `DoorWidth` 구간은 애초에 포인트를 만들지 않으므로 벽이 뚫린 것처럼 된다.
3. 문 위치에는 콜리전이 필요 없는 얇은 프레임(좌/우 세로 기둥 + 상인방)만 `Static Mesh Spawner`로
   장식용으로 얹는다. 실제로 여닫히는 문은 프로토타입 범위 밖이므로, 그냥 뚫린 개구부로 둔다.
4. 문 위치의 벽 세그먼트를 걸러내는 조건은 `Attribute Filter`나 `Density Filter`로 처리한다 —
   "이 포인트는 문이다"라는 불리언 속성을 만들어두면 이후 여러 노드에서 재사용하기 쉽다.

### 6.4 오픈사이드 파라펫(편복도 난간)

복도 반대쪽(외기 개방면)에는 벽 대신 허리 높이 박스(`ParapetHeight` = 110cm)를 세운다. 이 높이가
Character Movement의 기본 Max Step Height(약 45cm)를 넉넉히 초과하므로, **별도의 투명 블로킹
볼륨 없이 이 박스 하나만으로 추락 방지 콜리전이 충분하다** — 다만 카메라(3인칭이라면) 시야를
가리지 않는 높이인지 실제 플레이 테스트로 한 번 더 확인한다.

### 6.5 세대 내부 블록아웃 룸

프로토타입 범위에서는 세대 내부를 방 하나 수준으로만 구현한다. 현관 개구부를 지나 `UnitDepth`
만큼 들어간 위치에 바닥/좌우벽/후면벽/천장을 `Static Mesh Spawner`로 세운다. 창문은 6.3절과
동일한 "세그먼트 나눠 뚫기" 방식을 후면벽에 그대로 재사용할 수 있다(창은 문과 달리 바닥에서
일정 높이 위에서 시작하므로 세로 방향으로도 세그먼트를 하나 더 나눠야 한다) — 이번 라운드에서는
생략하고 다음 확장 과제로 남긴다.

## 7. 콜리전 & 내비게이션 메시 설정 (실제로 걸을 수 있게 만들기)

구조를 다 세워도 콜리전과 NavMesh가 맞지 않으면 플레이어는 벽을 통과하거나 복도에서 멈춰버린다.
확인이 필요한 지점은 다음과 같다.

### 7.1 기본 콜리전

`/Engine/BasicShapes/Cube`, `Plane` 등 엔진 기본 프리미티브는 기본적으로 `BlockAll` 콜리전
프리셋을 갖고 있으므로 별도 설정 없이도 벽/바닥으로 기능한다. Static Mesh Spawner 노드의
Static Mesh Descriptor에서 콜리전 프리셋이 의도치 않게 `NoCollision`으로 바뀌어 있지 않은지만
확인하면 된다.

### 7.2 Nav Mesh Bounds Volume

건물 전체(가로×세로×`FloorHeight`×`FloorCount` + 여유분)를 덮도록 `Nav Mesh Bounds Volume`을
배치한다. 층수가 많아지면 Z 방향 범위를 놓치기 쉬우므로, 파라미터의 `FloorCount × FloorHeight`
값을 참고해 볼륨 크기를 같이 맞춰둔다(가능하면 이 값도 데이터로 동기화).

### 7.3 Generation Trigger — 검증 단계에서는 Static(로드 시 1회 생성) 권장

PCG 컴포넌트의 Generation Trigger를 **Runtime/Dynamic**으로 두면 에디터 커뮤니티 포럼에서
보고된 회귀 이슈(5.6.1 기준, PCG가 스폰한 Instanced Static Mesh가 NavMesh 갱신을 자동으로
트리거하지 않는 문제)에 걸릴 수 있다. 구조 검증 단계에서는 **GenerateOnLoad(정적 생성)** 로
설정해 PCG가 먼저 다 생성된 뒤 NavMesh를 한 번 굽는 순서로 진행하는 것이 가장 안전하다.

런타임에 동적으로 재생성해야 하는 시점(예: 다른 평면 파라미터로 즉석 리롤)이 오면 다음 우회책을
알아두면 된다.

- PCG 그래프 생성 완료 이벤트(`OnGraphGenerated` 등)에서 스폰된 컴포넌트에 대해
  `SetCanEverAffectNavigation(true)` + `UpdateComponentInNavOctree`를 강제 호출.
- 또는 사각형 콜리전을 갖는 `NavModifier` 액터를 PCG 스폰 위치에 별도로 얹어 내비게이션
  갱신을 담당시키는 방법.
- NavMesh 자체를 Dynamic으로 설정해두는 것은 기본 전제이며, 위 두 방법은 "생성은 됐는데
  NavMesh가 못 알아채는" 증상에 대한 우회책이다.

### 7.4 ISM vs 개별 Static Mesh Actor

Static Mesh Spawner는 기본적으로 Instanced Static Mesh(ISM)로 스폰하는 편이 성능상 유리하지만,
ISM은 내비게이션 인식이 늦게 붙는 사례가 보고되어 있다. **블록아웃 검증 단계에서는 "Spawn as
Actors"(개별 Static Mesh Actor로 스폰)로 임시 설정해 내비게이션 문제부터 배제하고**, 구조와
동선이 검증된 뒤 최적화 단계에서 ISM으로 전환하는 순서를 권장한다.

### 7.5 좁은 개구부의 Agent Radius 확인

`DoorWidth` = 100cm는 NavMesh Agent Radius 기본값(약 34cm, 즉 통행에 필요한 폭은 대략
Agent Radius×2 + 여유)보다 충분히 넓지만, 코너나 문틀 프레임 장식 메쉬가 개구부 쪽으로 살짝
침범하면 Recast 복셀화 과정에서 개구부가 항행 불가로 판정될 수 있다. 실제로 캐릭터를 걸려서
테스트하고, 걸리면 문 폭을 넓히거나 Agent Radius/Cell Size를 조정한다.

## 8. 검증 체크리스트

- Nav Mesh Bounds Volume이 `FloorCount × FloorHeight` 전체를 여유 있게 덮고 있는가.
- 1층 로비 → 계단실 → 각 층 복도 → 세대 현관 → 세대 내부까지 캐릭터로 실제로 끊김 없이
  걸어갈 수 있는가 (복도-세대 바닥 단차 0 확인).
- 편복도 오픈사이드에서 파라펫을 넘어 추락하지 않는가.
- 문 개구부에서 캐릭터가 걸리지 않고 통과하는가 (7.5절 Agent Radius 확인).
- `MainGraph`와 `SG_Floor` 양쪽 모두 Attribute Partition 없이 Loop Subgraph에 데이터를
  바로 꽂는 실수가 없는가 (층/세대가 겹쳐서 생성되는 대표적 원인).
- Generation Trigger를 Static(GenerateOnLoad)으로 뒀을 때, 별도 재생성 없이 NavMesh가
  구조물 전체를 정확히 반영하는가.
- 파라미터(층수/세대수/복도폭 등)를 바꿔 다시 생성했을 때도 위 항목들이 모두 유지되는가
  (데이터 기반 설계가 실제로 재사용 가능한지 확인하는 방법).

## 10. 파사드 디테일 확장: 좌우 코어 계단 출입문 · 유리창 · 엘리베이터

1차 블록아웃(매스 + 층 슬래브 + 층마다 반복되는 코어 노치)까지 나온 뒤 이어서 붙이는 디테일이다.
세 가지 모두 "새 노드 종류"가 필요한 게 아니라, 5장·6장에서 이미 쓴 **세그먼트 나눠 배치하기** 패턴을
코어 벽과 파사드 벽에 한 번 더 적용하는 것으로 해결된다.

### 10.1 계단실 출입문 (코어 벽에 개구부 내기)

지금 코어는 5.1절 기준으로 "계단실 매스 박스 1개"를 통짜로 스폰하고 있을 것이다. 문을 내려면
그 박스를 통짜로 두지 말고, 6.3절에서 세대 현관에 썼던 것과 같은 방식으로 **코어의 복도측 벽만
별도 포인트로 분리**한다.

- 코어 폭(`CoreWidth`)에서 `DoorWidth`를 뺀 나머지를 좌/우 벽 세그먼트로 나눠 두 개의
  `Static Mesh Spawner`로 스폰하고, 가운데 `DoorWidth` 구간은 포인트를 아예 만들지 않는다
  (= 뚫린 개구부).
- 건물 양 끝에 코어가 각각 있다면(좌측 코어/우측 코어), 같은 로직을 **Transform Points로
  미러링**해서 재사용하면 그래프를 두 번 짤 필요가 없다 — 5.2절에서 좌/우 세대열을 미러링한 것과
  동일한 방법이다.
- 문 위치의 바닥은 복도 바닥과 단차 없이 이어지게 한다(6.1절과 같은 이유 — Max Step Height
  초과 시 캐릭터가 못 지나감).
- 프로토타입 단계라 실제로 열리는 문짝은 필요 없다. 개구부만 뚫려 있으면 통과 가능하고,
  장식으로 얇은 문틀(좌/우 세로 기둥 + 상인방)만 얹어도 충분하다.

### 10.2 유리창 (파사드 벽의 수직 방향 추가 분할)

6.5절에서 "다음 과제"로 미뤄뒀던 부분이다. 지금까지는 문 때문에 벽을 **가로(X축) 로만** 좌/우
두 조각으로 나눴는데, 창을 넣으려면 **세로(Z축)** 로도 한 번 더 나눠야 한다.

- 창이 들어갈 벽 세그먼트를 세로로 3단 분할한다: 하단 허리벽(예: 바닥에서 90cm, 솔리드),
  창 구간(예: 다음 120cm, 포인트를 만들지 않거나 얇은 유리 패널 메쉬로 대체), 상단 인방
  (천장까지, 솔리드).
- 블록아웃 단계에서 "유리"를 표현하는 가장 빠른 방법은 그 구간에 별도의 얇은 Cube를 하나 더
  스폰하고 Static Mesh Descriptor에서 반투명/유닛 컬러 머티리얼(예: 옅은 하늘색 Unlit)을
  임시로 지정하는 것이다. 실제 유리 메쉬/머티리얼로 교체하는 건 나중 디테일 패스에서 이
  포인트 위치를 그대로 재사용하면 된다.
- 코어 노치 부분(계단실 외벽)에도 같은 방식으로 창을 낼 수 있다 — 계단실은 채광이 중요한
  자리라 실제로도 창이 많이 들어간다.

### 10.3 엘리베이터 (별도 샤프트 + 층별 문)

5.1절에서 "엘리베이터 샤프트 매스 박스 1개"로 뭉뚱그렸던 부분을 구체화한다.

- 계단실 옆에 별도의 샤프트 박스(`Static Mesh Spawner`, 층고×`FloorCount` 전체 높이로 한
  번에 세워도 되고 층마다 반복해도 됨 — 어차피 통짜 매스라 시각적 차이는 없음)를 코어 폭
  안쪽에 배치한다.
- 샤프트의 복도측 면에 **층마다** 문 폭만큼 개구부를 낸다 — 10.1절과 완전히 같은
  "세그먼트 나눠 배치" 패턴이다. 이 문은 실제로 열리고 닫히는 엘리베이터 문이 아니라, 지금은
  "여기 엘리베이터가 있다"를 표시하는 개구부 정도로 충분하다.
- 프로토타입에서는 엘리베이터 내부(카 내부)까지 걸어 들어갈 필요는 없으므로, 개구부 안쪽은
  얕은 깊이(50~80cm)의 벽으로 막아두면 된다 — 안으로 캐릭터가 들어갔다가 못 나오는 상황을
  방지한다.

### 10.4 검증 추가 항목

- 8장 체크리스트에 다음 세 줄을 추가해서 확인한다.
- 좌/우 코어 출입문 모두 캐릭터가 걸리지 않고 통과하는가 (10.1).
- 창 개구부가 콜리전을 남기지 않고 완전히 뚫려 있는가, 혹은 유리 패널이 캐릭터를 막지 않는
  머티리얼/콜리전 설정인가 (10.2).
- 엘리베이터 개구부에 들어갔을 때 막다른 벽에 자연스럽게 막히고, NavMesh가 그 안쪽까지
  "갈 수 있는 공간"으로 잘못 표시하지 않는가 (10.3).

## 11. 계단실 실제 계단 블록아웃: 전형적인 꺾음계단(반턴계단) 형태

지금까지 결과물은 코어 자리가 매스/노치로만 표현돼 있고 실제 계단 단이 없는 상태다. 한국
복도식 아파트의 전형적인 계단실은 대부분 **꺾음계단(반턴계단, dog-leg stair)** 형태다 — 한 층을
오르는 동안 한 방향으로 절반을 오른 뒤 중간 계단참(landing)에서 180도 꺾어 반대 방향으로 나머지
절반을 오른다. 또한 채광·환기를 위해 대부분 옥외에 개방되어 있어서, 계단과 계단참 옆면이 밖에서
훤히 보이는 게 특징이다 — 지금 스크린샷의 세로 슬릿/노치가 바로 그 개방된 부분이다.

### 11.1 파라미터 추가

- `StairRiser` (float, cm) = 18 — 한 단 높이(챌판)
- `StairTreadDepth` (float, cm) = 28 — 한 단 깊이(디딤판)
- `StairWidth` (float, cm) = 120 — 계단 폭
- `LandingDepth` (float, cm) = 150 — 중간 계단참 깊이
- `StepsPerFlight` = `(FloorHeight / 2) / StairRiser`를 반올림한 정수(그래프 안에서 정수 나눗셈
  + 반올림으로 계산). 기본값 기준 300cm/2=150cm, 150/18 ≈ 8.3 → 8~9단.

### 11.2 한 개 층 분량 계단(Flight A + 계단참 + Flight B) 만들기

가장 다루기 쉬운 방법은 **경사진 스플라인 하나를 만들고 그 위에서 일정 간격으로 포인트를 뽑는
것**이다. 문/창에서 쓴 "가로로 세그먼트 나눠 배치하기"와 달리, 계단은 오르막이라 스플라인
기반이 훨씬 깔끔하다.

1. Flight A용 스플라인 2점을 그린다: 시작점 `(0,0,0)`, 끝점
   `(StepsPerFlight × StairTreadDepth, 0, StepsPerFlight × StairRiser)` — 수평으로
   `StepsPerFlight`단만큼 가면서 동시에 수직으로 그만큼 올라가는 직선 스플라인이다.
2. **Get Spline Data**로 이 스플라인을 PCG에 가져오고, **Spline Sampler**를 "포인트 개수 =
   StepsPerFlight" 모드로 설정해 균등 간격으로 포인트를 뽑는다. 스플라인이 일정 기울기의
   직선이므로, 뽑힌 포인트들은 자동으로 "한 단씩 앞으로+위로" 이동한 형태가 된다.
3. Spline Sampler는 기본적으로 스플라인 접선 방향으로 포인트를 회전시키므로(경사만큼 피치가
   기울어짐), **Transform Points**로 Pitch/Roll을 0으로 되돌려 디딤판이 수평을 유지하도록
   보정한다(Yaw만 남긴다).
4. 각 포인트에 `Static Mesh Spawner`(Cube, `StairWidth × StairTreadDepth × StairRiser` 크기)를
   스폰한다 — 디딤판 하나하나가 그 자체로 챌판까지 포함한 통짜 계단 블록이 되어, 콜리전도
   자동으로 계단 모양을 따라간다.
5. Flight A 끝 지점(맨 위)에 **계단참**을 놓는다: `Static Mesh Spawner`(Cube,
   `StairWidth×2 × LandingDepth`)를 Flight A 끝 높이(Z = `FloorHeight`/2)에 배치.
6. Flight B는 Flight A와 동일한 그래프를 **Transform Points로 180도 회전 + 계단참 위치로 이동**해서
   재사용한다(5.2절, 10.1절에서 좌/우를 미러링했던 것과 완전히 같은 패턴). Flight B는 계단참에서
   시작해 다음 층 바닥 높이(Z = `FloorHeight`)까지 올라간다.
7. 이 Flight A + 계단참 + Flight B 묶음을 **SG_Stair** 서브그래프로 감싸서, 5.1절의 "계단실 매스
   박스"를 대체한다. SG_Floor는 이미 층마다 반복되고 있으므로 SG_Stair도 자동으로 층마다
   반복된다.
8. 건물 양 끝(또는 중앙 코어가 두 방향으로 뻗어 있다면 그 두 곳)에 SG_Stair를 배치할 때도
   10.1절과 같은 방식으로 **Transform Points 미러링**을 써서 그래프를 두 번 짤 필요가 없게 한다.

### 11.3 개방형 계단실의 추락 방지 난간

한국 복도식 아파트 계단실은 대부분 옥외 개방형이라 계단과 계단참의 옆면이 뚫려 있다. 6.4절에서
쓴 파라펫(`ParapetHeight` = 110cm)과 똑같은 박스를 계단 각 단의 개방된 옆면과 계단참 가장자리를
따라 세운다 — 스플라인을 따라가는 구조이므로, 계단 스텝을 스폰할 때 쓴 것과 같은 포인트 목록에
옆으로 `StairWidth/2 + 파라펫두께/2`만큼 오프셋한 위치로 파라펫 포인트를 하나 더 만들면 된다.

### 11.4 콜리전/내비게이션 참고 사항

- `StairRiser` = 18cm는 Character Movement의 기본 Max Step Height(약 45cm)보다 한참 작으므로,
  Recast NavMesh가 계단 단 하나하나를 별도 램프 콜리전 없이도 "걸어 오를 수 있는 계단"으로
  인식한다. 즉 11.2절의 통짜 스텝 박스 방식만으로 추가 조치 없이 걸어서 오르내릴 수 있어야 한다.
- 실제 플레이 테스트에서 계단을 오를 때 캐릭터가 매 단마다 미세하게 걸리는 느낌이 나면,
  `StairRiser`를 낮추거나(예: 15cm) Nav Mesh Agent의 `Max Step Height`를 프로젝트 설정에서
  살짝 올려서 비교해본다.
- 계단참(landing)과 계단 발판 사이에 단차가 없는지(6.1절과 같은 이유로) 반드시 확인한다.

### 11.5 검증 추가 항목

- 좌/우(또는 양 끝) 계단실 모두 1층부터 최상층까지 실제로 걸어 오를 수 있는가.
- 계단참에서 180도 꺾이는 지점에서 캐릭터가 자연스럽게 방향을 바꿔 이동할 수 있는가(부딪히거나
  걸리지 않는가).
- 개방된 계단 옆면에서 파라펫을 넘어 추락하지 않는가.

## 12. 트러블슈팅: 계단 입구가 벽에 가려지거나 양쪽에 생성되지 않을 때

11장 구현 후 실제로 자주 나오는 두 가지 증상과 원인이다. 둘 다 "그래프가 잘못 짜였다"기보다는
**서로 다른 절에서 독립적으로 계산한 좌표/데이터가 어긋나거나 병합이 빠진 것**이 원인인 경우가
대부분이다.

### 12.1 증상 A — 계단 입구가 벽에 가려짐

10.1절(코어 벽에 문 폭만큼 개구부 내기)과 11.2절(스플라인 기반 계단 Flight)은 원래 서로 다른
로컬 좌표 기준으로 각각 개구부 위치/계단 시작 위치를 계산했을 가능성이 높다. 이 둘의 기준점이
어긋나면, 코어 벽에는 분명 문 폭만큼 뚫려 있는데 그 뚫린 자리와 실제 계단 Flight A의 시작 위치가
살짝 어긋나서 "복도에서 볼 땐 뚫려 있는데 그 앞에 다른 벽(격벽·문틀·엘리베이터 샤프트 벽 등)이
겹쳐서" 막힌 것처럼 보이는 증상이 나온다. 확인 순서:

1. 코어 벽 개구부의 로컬 X 중심 좌표와 Flight A 스플라인 시작점의 로컬 X 좌표를 각각 출력해서
   비교한다(PCG 디버그 표시 또는 Attribute Debug 노드로 확인). 두 값이 다르면 그게 원인이다.
2. 근본 해결책은 두 절이 **같은 기준 속성 하나**(예: `DoorCenterX`)를 공유하도록 그래프를 고쳐서,
   10.1절의 벽 세그먼트 분할과 11.2절의 스플라인 시작점이 항상 같은 값에서 파생되게 만드는 것이다
   — 좌표를 두 군데서 따로 계산하지 않는다.
3. 좌표가 일치하는데도 막혀 보인다면, 10.1절에서 만든 "장식용 문틀"(좌/우 세로 기둥 + 상인방)의
   기둥 폭이 실수로 `DoorWidth` 전체만큼 넓게 스케일되어 있는지 확인한다 — 장식 프레임은 개구부
   가장자리의 얇은 테두리여야지, 개구부 전체를 덮는 크기가 되면 안 된다.
4. 그래도 막혀 있다면 엘리베이터 샤프트 벽(10.3절)이나 세대 간 격벽(6.2절)이 같은 자리에 겹쳐
   스폰되고 있지 않은지 확인한다 — 서로 다른 절에서 만든 벽 스포너 3~4개가 좌표 계산 실수로
   같은 위치에 겹치는 것은 이런 다단계 그래프에서 가장 흔한 버그다.

### 12.2 증상 B — 계단이 한쪽(중앙)에만 생기고 양옆에 생기지 않음

10.1절·11.2절 모두 "그래프를 두 번 짜지 말고 Transform Points로 미러링해서 재사용"하라고
했는데, 실제로 양쪽에 생성되지 않는다면 다음 중 하나일 가능성이 크다.

1. **코어 위치 포인트 자체가 1개만 생성됨**: 좌/우 코어 위치를 만드는 단계(원래는 건물 양 끝에
   포인트 2개가 있어야 함)에서 개수가 1로 되어 있거나, 필터 조건이 한쪽을 걸러내고 있을 수
   있다. 이 포인트 개수를 Attribute Debug로 먼저 확인한다 — 2개가 맞는지가 첫 확인 사항.
2. **미러링된 쪽 브랜치의 출력이 Merge에 연결되지 않음**: PCG에서 가장 흔한 실수 중 하나다.
   Transform Points로 왼쪽 브랜치를 만들어놓고 그 출력을 최종 Merge/출력 노드에 연결하는 걸
   빠뜨리면, 계산은 정상적으로 되는데 레벨에는 아무것도 안 나온다("생성이 안 되는" 것처럼 보이는
   가장 흔한 원인). SG_Stair를 감싸는 그래프에서 왼쪽·오른쪽 두 브랜치가 모두 하나의 Merge
   노드를 거쳐 최종 출력으로 이어지는지 확인한다.
3. **Loop Subgraph에 파티션이 빠짐**: 3장에서 강조한 것과 같은 문제다. 코어 위치 포인트 2개를
   파티션 없이 그대로 SG_Stair 호출에 꽂으면 2개가 하나로 뭉쳐 처리되어 결과적으로 한쪽만(혹은
   둘이 겹쳐서 하나처럼) 생성된 것처럼 보일 수 있다. `Attribute Partition`이 코어 인덱스 기준으로
   제대로 걸려 있는지 다시 확인한다.

### 12.3 디버깅 순서 요약

1. 코어 위치 포인트 개수부터 확인 (2개인가?).
2. 그 2개가 Attribute Partition을 거쳐 Loop Subgraph에 들어가는가?
3. 양쪽 브랜치 출력이 모두 최종 Merge에 연결돼 있는가?
4. 코어 벽 개구부 좌표와 계단 Flight 시작 좌표가 같은 기준값에서 나오는가?
5. 장식용 문틀·엘리베이터 샤프트 벽·격벽이 개구부 자리를 침범하지 않는가?

## 13. 실측 확인된 제약: 이 프로젝트의 Unreal MCP 툴은 Loop Subgraph를 만들지 못한다

Claude Code가 실제 그래프를 열어 확인한 결과, 이 프로젝트에서 쓰는 MCP 그래프 편집 API는
**Loop 노드의 `subgraphInstance` 속성을 설정할 수 없어서 Attribute Partition + Loop Subgraph
조합 자체를 만들 수 없다** (Loop이 요구하는 `PCGGraphInstance` 객체를 툴이 생성하지 못함). 그
결과 실제 그래프(`PCG_Apartment_Main` / `_Floor` / `_Stair`)는 3~5장에서 설명한 패턴 대신
**일반 Subgraph 노드 + Copy Points로 좌표를 복제해서 한 번에 배치("cartesian-stamp")하는 방식**
으로 대체되어 있다. 포인트 개수가 적은 지금 규모에서는 기능적으로 동등하지만, 이 방식에서는
Partition이 자동으로 해주던 "브랜치별 개별 처리"를 **사람이 직접 여러 개의 명시적 브랜치로
나눠 만들고, 각 브랜치를 빠짐없이 최종 Merge에 연결**해야 한다. 3~5장, 10~11장의 "Attribute
Partition → Loop Subgraph"라는 표현이 나오면, 이 프로젝트에서는 실제로 "포인트마다 하나씩,
사람이 명시적으로 만든 별도 브랜치 + Merge"로 대체됐다는 뜻으로 읽으면 된다.

이 제약 때문에 11장의 계단 Flight A/B도 자동으로 둘 다 생기지 않는다 — Flight A용 브랜치를
만들었다면 Flight B용 브랜치를 **별도로 하나 더** 만들어서 Merge에 연결해야 하며, 이걸
빠뜨리면 "계단 한쪽만 생기고 반대쪽은 안 생기는" 정확히 이번에 나온 증상이 재현된다.

### 13.1 지금 증상에 적용: 계단 Flight B가 통째로 빠져 있음

Claude Code의 보고에 따르면 `SG_Stair`(`StairLocalTemplate`) 안에는 Flight A(로컬 X=-65
기준) 하나만 확인됐고, 계단참 반대편에서 다음 층까지 올라가는 Flight B는 언급되지 않았다.
"양옆에 계단이 생성되어야 하는데 생성 안 됨"의 실제 원인은 10.1/10.2절에서 걱정했던 "코어가
양 끝에 있는데 한쪽만 생성" 문제가 아니라, **애초에 이 프로젝트 구조는 코어 1개(1.1/5.1/5.2절
설계대로)이고, 그 코어 안의 꺾음계단 두 Flight 중 하나(Flight B)가 그래프에 아예 없는 것**이다.

조치: `SG_Stair` 안에 Flight A 포인트 세트를 **복제(Copy Points) → Transform Points로 180도
회전 + 계단참 반대쪽 끝으로 이동**한 새 브랜치를 하나 더 만들고, 이 브랜치의 출력을 Flight A·
계단참과 함께 하나의 Merge Points 노드로 모아 `SG_Stair`의 최종 출력으로 내보낸다. Loop을 쓸 수
없으므로 이건 그래프에 노드 몇 개를 명시적으로 더 그려 넣는 작업이다.

### 13.2 계단 통로 한가운데를 막는 벽

스크린샷에서 빨간 선으로 표시된, 계단 통로 중앙을 위아래로 가로지르는 전체 층고 높이의 수직
벽 패널은 사람이 실제로 오르내릴 통로 자리에 있으면 안 된다. 유력한 후보는 두 가지다.

- **엘리베이터 샤프트 벽(10.3절)** — DoorCenterX를 -125에서 -190으로 옮기면서 계단 Flight
  위치는 다시 계산했지만, 엘리베이터 샤프트 벽은 예전 좌표를 그대로 쓰고 있어서 결과적으로
  통로 한복판에 남아있을 가능성이 크다.
- **코어 벽 세그먼트(10.1절, `CoreLocalTemplate`)의 잔여 조각** — DoorCenterX 수정 후 좌/우
  세그먼트 폭은 다시 계산했다고 보고했지만, 그 세그먼트들의 Z 범위(층고 전체)가 계단 통로 폭과
  겹치는 위치까지 뻗어있지 않은지 다시 확인이 필요하다.

조치: `SG_Stair`와 `CoreLocalTemplate` 안의 모든 Static Mesh Spawner 템플릿을 나열해서, 로컬
X 범위가 "Flight A와 Flight B 사이의 통로 폭"과 겹치면서 Z 범위가 층고 전체에 걸쳐 있는 것을
찾는다. 찾으면 그 벽을 통로 바깥(엘리베이터 샤프트 쪽 또는 벽 안쪽)으로 옮기거나, 통로와 겹치지
않는 만큼만 남도록 X 범위를 줄인다 — 이때 반드시 13.1절에서 확정한 새 Flight A/B 좌표를
기준으로 다시 계산해서, 12.1절에서 지적한 것과 같은 "따로 계산해서 어긋나는" 문제가 재발하지
않게 한다.

## 14. 설계 수정: 코어(계단실) 2개, 건물 양 끝에 배치

여러 턴에 걸친 디버깅 끝에 확인된 사실: "좌우에 계단"이라는 요청은 "코어 1개 안의 꺾음계단
Flight A/B"가 아니라 **건물 양 끝에 각각 별도의 코어(계단실)가 있어야 한다**는 뜻이었다(사용자
확정). Flight A/B 자체는 Claude Code가 이미 클린 리제너레이트 + 월드좌표 대조까지 마쳐서 정상
동작이 확인됐으므로, SG_Stair 서브그래프(11장)는 그대로 재사용하고 **그걸 부르는 코어 위치를
1개에서 2개로 늘리는 것**이 이번 변경의 전부다. 즉 "버그 수정"이 아니라 "층 평면 자체를
다시 배치하는" 작업이다.

### 14.1 무엇이 바뀌는가

- **코어**: 기존에는 건물 중앙에 코어 1개, 거기서 좌우로 복도가 뻗어나가는 구조(5.2절)였다.
  이제는 건물 양 끝에 코어 A / 코어 B를 각각 두고, 그 사이를 복도 하나가 잇는 구조로 바뀐다.
- **세대열**: 기존에는 "중앙 코어 기준 좌/우로 각각 `UnitsPerSide`개씩" 배치했다(5.2절). 이제는
  "코어 A의 안쪽 끝 ~ 코어 B의 안쪽 끝 사이에 세대를 일렬로" 배치하는 방식으로 바뀐다. 총
  세대수(현재 6가구)는 그대로 유지할지, 건물 길이에 맞춰 늘릴지는 실제 코어 A/B 사이 거리를
  본 뒤에 정한다.
- **SG_Stair 자체**: 바뀌지 않는다. Flight A/B, 계단참, 슬릿 가드 모두 지금 구조 그대로 코어
  A/B 양쪽에 재사용한다.

### 14.2 그래프 변경 절차 (13장의 "Loop 미지원" 제약을 그대로 적용)

이 프로젝트의 MCP 툴은 Loop Subgraph를 못 만든다(13장)는 게 이미 확인됐으므로, "코어가
1개에서 2개로 늘어난다"는 것도 자동 반복이 아니라 **명시적으로 브랜치를 하나 더 그려서
Merge에 연결**하는 방식으로 처리한다.

1. 기존 `StairAnchorPoint`(코어 A, 로컬 `(-125, 0, 0)`)는 그대로 둔다.
2. 건물 반대쪽 끝에 `StairAnchorPoint_B`를 새로 만든다. 좌표는 건물 전체 폭 기준으로 코어 A와
   대칭이 되는 위치로 계산한다(예: 건물 폭이 `W`라면 코어 B의 로컬 X는 `W - 125` 근처가 되도록
   — 정확한 값은 지금 그래프의 실제 유닛/코어 폭 합산치를 Claude Code가 직접 조회해서 계산해야
   한다. 손으로 추정한 숫자를 그대로 쓰지 말 것).
3. `Call_Stair`를 코어 A용과 완전히 동일하게 한 번 더 인스턴스화해서 `StairAnchorPoint_B`에
   연결한다 — 10.1절에서 좌/우 문을 미러링했던 것과 같은 "그래프 복제" 패턴이다. 코어 B의 계단이
   코어 A와 같은 방향으로 복도를 바라봐야 한다면 Transform Points로 Yaw 180도 회전이 필요한지
   먼저 확인한다(코어 A는 복도를 향해 열리는데, 단순히 위치만 옮기면 반대 방향을 보게 될 수
   있다).
4. 코어 B 브랜치의 출력을 코어 A 브랜치와 같은 최종 Merge Points 노드에 연결한다 — 13.1절에서
   지적한 것과 같은 "브랜치 만들고 Merge 연결을 빠뜨리는" 실수가 여기서도 가장 흔하게 나온다.
5. 세대열 생성 로직(5.2절 해당 부분)을 "코어 A 안쪽 끝 좌표 ~ 코어 B 안쪽 끝 좌표" 사이에
   세대를 채우는 방식으로 다시 계산한다. 지금처럼 "중앙 코어에서 좌우로 각각 뻗는" 코드를 그대로
   두고 코어 위치만 바꾸면 세대열이 코어 A/B와 겹치거나 건물 밖으로 나가므로, 이 부분은 반드시
   좌표 재계산이 필요하다.
6. 10.1절(문 개구부)·10.3절(엘리베이터)도 코어 A뿐 아니라 코어 B에도 동일하게 적용돼 있는지
   확인한다 — 지금까지 모든 디테일 작업이 코어 A 기준으로만 이뤄졌으므로, 코어 B는 이 디테일들이
   전부 빠진 "매스 박스" 상태일 가능성이 높다.

### 14.3 검증

- 클린 리제너레이트 후, 코어 A와 코어 B 양쪽 모두에서 1층부터 최상층까지 실제로 걸어 오를 수
  있는가.
- 두 코어 사이 복도에 배치된 세대들이 코어 벽과 겹치지 않는가.
- 코어 B에도 문 개구부·엘리베이터·창이 코어 A와 동일하게 적용돼 있는가.
- 건물 외부에서 봤을 때 양 끝에 계단실 특유의 개방된 슬릿/노치가 대칭으로 보이는가.

## 15. 계단실 수직 개구부(Shaft Void)와 헤드룸(Clearance) 확보

플레이 테스트 스크린샷: 캐릭터가 계단을 오르다가 위층 바닥/천장에 머리가 막혀 더 못 올라간다.
11장까지의 작업은 "계단 단이 걸을 수 있는 형태로 있는가"만 검증했지, **그 계단 위 공간에
다른 층의 바닥 슬래브나 계단참이 통행을 막지 않는가**는 아직 확인한 적이 없다. 원인은 둘 중
하나(또는 둘 다)다.

### 15.1 원인 A — 층 슬래브가 계단 통로 자리까지 통짜로 덮고 있음

실제 건물의 계단실은 계단이 지나가는 자리(두 Flight의 평면 투영 영역)만큼은 **각 층 바닥
슬래브에 뚫린 수직 관통 구멍(shaft void)**이어야 한다. 그래야 아래층 Flight B를 다 오른
캐릭터가 위층 바닥을 뚫지 않고 자연스럽게 위층 복도 레벨로 올라선다. 지금 5.1절의 "코어 전실
바닥 슬래브"가 코어 폭(`CoreWidth`) 전체를 통짜 사각형으로 매 층마다 스폰하고 있다면, 이
사각형이 바로 아래층 Flight A/B가 지나가야 할 자리까지 덮어버려서 천장처럼 막힌 것으로 보인다.

조치:

1. 코어 전실 바닥 슬래브를 "통짜 `CoreWidth × 코어 깊이`"에서 **Flight B가 도착하는 지점 바로
   앞의 작은 도착 발판**(대략 `StairWidth × 150cm` 정도)만으로 줄인다.
2. 나머지 코어 평면 영역(두 Flight가 지나가는 X/Y 범위 전체)은 그 층 Z 레벨에서 **아예 포인트를
   만들지 않는다** — 이게 진짜 수직 개구부(shaft)다. 계단참(11.2절의 landing)은 층과 층 사이
   중간 높이에 있으므로 이 규칙과 무관하게 그대로 둔다.
3. 이 처리를 최상층을 제외한 모든 층(1층 슬래브~`FloorCount`-1층 슬래브)에 적용한다. 최상층
   위에는 오를 곳이 없으므로 지붕은 통짜로 둬도 된다.
4. 14장에서 코어가 2개가 됐으므로, 코어 A·코어 B 양쪽 모두에 동일하게 적용한다.

### 15.2 원인 B — 계단참/반대편 Flight의 헤드룸(수직 여유 공간) 부족

원인 A를 고쳐도 여전히 막힌다면, 이번엔 **계단참이나 반대쪽 Flight의 밑면이 낮게 내려와서
지나가는 사람 머리 높이와 겹치는** 헤드룸 문제일 수 있다. 이 프로젝트처럼 두 Flight가 나란히
붙어 마주보고 오르내리는 "겹침형(scissor) 꺾음계단"에서는, Flight A를 오르는 사람의 머리 위로
Flight B(또는 그 위 계단참)의 밑면이 지나가므로, **Flight A의 매 단마다 그 바로 위에 있는
Flight B/계단참 밑면까지의 수직 거리가 최소 210cm 이상**이어야 한다(실무 건축 기준으로 흔히
쓰이는 값). 지금 그래프는 이 수치를 계산에 넣지 않았을 가능성이 높다.

조치: Flight A의 각 단(seed 201~208 등) 좌표에서 수직으로 올라가며 가장 먼저 만나는 solid
지오메트리(계단참 밑면, Flight B의 스텝 박스 밑면 등)까지의 Z 거리를 전부 계산해서, 210cm
미만인 지점이 있는지 확인한다. 있다면 다음 중 하나로 해결한다.

- 계단참 높이를 살짝 올리거나 낮춰서 두 Flight 사이 수직 간격을 재배치한다.
- 계단실 전체 깊이(`CoreWidth`/`Y` 방향 치수)를 늘려서 Flight 런(run) 길이를 길게 하고,
  그만큼 한 단당 실제 리저 수를 자연스럽게 조정한다.
- 이 프로젝트 규모(프로토타입, `FloorHeight`=300cm)에서는 두 방법 다 큰 치수 변경 없이
  가능한 수준이므로, 헤드룸 210cm를 만족하는 선에서 `StairRiser`/`StepsPerFlight`/계단참
  높이를 함께 재조정하는 게 가장 빠르다.

### 15.3 검증

- 각 Flight의 모든 단을 순서대로 밟아 올라가면서, 캐릭터가 어디에서도 위쪽 지오메트리에
  가로막히지 않는가(플레이 테스트로 직접 끝까지 걸어 올라가 확인).
- 층 슬래브에 뚫린 개구부가 정확히 계단 통로 위치와 일치하는가(15.1절에서 만든 개구부와
  11.2절의 Flight 평면 좌표가 같은 기준에서 나왔는가 — 12.1절에서 강조한 "좌표 공유" 원칙을
  여기서도 적용).
- 최상층 지붕만 예외적으로 통짜로 남아있고, 나머지 층은 전부 개구부가 있는가.

## 16. 엔드 유닛(코어와 맞닿은 세대)의 코어측 벽 누락

15장 개구부 작업 이후 스크린샷: 코어(계단실)와 바로 맞닿은 세대(엔드 유닛)의 코어 쪽 벽이
뚫려 있어서, 그 세대 내부 공간이 계단 통로 공간과 시각적으로도 실제로도 겹친다.

### 16.1 원인

6.2절의 "세대 간 격벽"은 **유닛과 유닛 사이** 경계만 다룬다. 유닛 열의 양 끝, 즉 **엔드
유닛과 코어 사이의 경계벽**은 지금까지 어느 절에서도 명시적으로 다룬 적이 없다 — 5.2절(중앙
코어 1개) 설계에서는 이 경계를 코어 쪽 벽(10.1절)이 대신 막아준다고 암묵적으로 가정했는데,
14장에서 "코어 2개 + 그 사이를 채우는 세대열" 구조로 바뀌면서 코어 A/코어 B 양쪽 다 이
가정이 맞는지 다시 확인된 적이 없다. 게다가 코어 B 쪽은 미러링(Transform Points 180도)으로
만들어졌으므로, 좌/우 부호가 반대로 계산돼 벽이 반대쪽에 생기거나 아예 안 생겼을 가능성이
크다.

### 16.2 조치

1. 유닛 열의 양쪽 끝(코어 A와 맞닿는 첫 유닛, 코어 B와 맞닿는 마지막 유닛) 각각에, 6.2절과
   같은 규격(`Static Mesh Spawner`, 두께=`WallThickness`, 높이=`FloorHeight`)의 벽을
   **코어와 유닛 열 사이 경계**에 하나씩 명시적으로 추가한다. 이건 6.2절의 "유닛 간 격벽"과는
   별개의, "유닛-코어 경계벽"이라는 새 템플릿으로 다루는 게 헷갈리지 않는다.
2. 이 벽의 로컬 X 좌표는 "그 코어의 안쪽 끝 좌표"에서 그대로 가져와야 한다(14.2절에서 세대열
   시작/끝 좌표를 코어 안쪽 끝 기준으로 재계산했던 바로 그 값). 좌표를 새로 추정하지 말고 이미
   계산해 둔 코어 안쪽 끝 값을 그대로 재사용한다 — 12.1절에서 지적한 "따로 계산해서 어긋나는"
   문제를 반복하지 않기 위함이다.
3. 13장 제약(Loop 미지원) 그대로, 코어 A쪽 벽과 코어 B쪽 벽을 **각각 명시적인 별도 브랜치**로
   만들고 둘 다 최종 Merge에 연결한다. 코어 B쪽은 미러링에서 좌/우 부호가 뒤집힐 수 있으므로,
   벽이 코어 쪽을 향해 정확히 막고 있는지(반대쪽 외벽 자리에 실수로 생기지 않았는지) 좌표를
   직접 확인한다.

### 16.3 검증

- 코어 A·코어 B 양쪽 엔드 유닛 모두, 유닛 내부에서 코어(계단실) 쪽을 봤을 때 벽으로 완전히
  막혀 있는가.
- 엔드 유닛 내부에서 코어 방향으로 걸어가도 계단 통로로 넘어가지지 않는가(콜리전 기준 확인).
- 이 벽 추가로 인해 세대 내부 블록아웃 룸(6.5절)의 치수가 코어 쪽으로 침범하지 않는가.

## 17. 코어 A/B 대칭성 감사 · 계단실 내 미완성 공간 · 헤드룸 재검토

16장까지 코어 B(미러링으로 만든 쪽)에서 계속 개별적인 누락/오배치가 하나씩 발견돼 왔다
(Flight B 누락 오인 → 통로 차단 벽 오인 → 엔드 유닛 벽 누락 → 이번엔 난간 뚫림 + 좌우
비대칭 구조물). 이제는 **하나씩 땜질하기보다 코어 A와 코어 B를 통째로 대조하는 감사**가 더
빠르다.

### 17.1 증상 1 — 코어 A/B 비대칭 (좌측엔 있는 구조물이 우측엔 없고, 대신 난간이 뚫림)

이건 13장에서 이미 여러 번 나온 "미러링 시 좌/우 부호가 뒤집혀서 엉뚱한 자리에 생기거나 아예
안 생기는" 문제의 또 다른 사례로 보인다. 다만 이번엔 개별 요소 하나가 아니라 **코어 B 쪽
브랜치 전체에 이런 누락이 몇 개나 더 있는지 알 수 없는 상태**이므로, 다음처럼 감사 방식으로
접근한다.

1. 코어 A 브랜치에 연결된 모든 템플릿(포인트 세트)을 이름·로컬 좌표·크기와 함께 나열한다.
2. 코어 B 브랜치에 연결된 모든 템플릿을 동일하게 나열한다.
3. 두 목록의 **개수가 같은지** 먼저 확인한다(코어 A에는 있는데 코어 B 목록에 대응 항목이
   없다면 그게 "구조물 누락"이다).
4. 개수가 같다면, 코어 B의 각 항목 좌표가 "코어 A 좌표를 건물 중심 기준으로 미러링한 값"과
   정확히 대칭인지 하나씩 대조한다(부호만 반대인지, 아니면 축 자체가 잘못 미러링됐는지).
5. 난간(파라펫)처럼 원래 "막혀 있어야 하는" 요소가 코어 B 쪽에서 문(개구부)으로 취급돼
   구멍이 난 경우는, 그 요소에 실수로 "이건 문이다" 불리언 속성이나 필터 조건이 잘못 상속된
   경우가 많다(10.1절의 문 개구부 필터 로직이 난간 템플릿에도 잘못 적용됐을 가능성).

### 17.2 증상 2 — 계단실 안에 "아무것도 없는" 미완성 공간

스크린샷(3번째 사진, "추가" 표시)에는 계단실 내부인데 바닥도 계단도 없이 그냥 뚫려 있는
구간이 있다. 이건 15장에서 의도적으로 만든 shaft void(계단이 지나가는 자리를 일부러 비우는
것)와는 다르다 — 그쪽은 "계단이 지나가야 할 자리를 비웠다"였고, 이번 건 "계단이든 바닥이든
뭔가 있어야 할 자리인데 아무것도 없다"는 것이다.

조치: 코어 A/B 각각의 평면 영역을 층별로 나눠서, 그 안의 모든 X/Y 지점이 다음 중 하나로
분류되는지 확인한다 — ① Flight A 발판, ② Flight B 발판, ③ 계단참, ④ 15장에서 의도한 shaft
void(개구부), ⑤ 코어 외벽/문/난간. 이 다섯 가지 어디에도 속하지 않는 "미분류 영역"이 남아
있다면 그게 스크린샷의 빈 공간이다 — 대개 Flight 하나의 포인트 개수/범위가 코어 전체 깊이를
다 못 채우고 중간에 끊겨서 생기는 경우가 많으므로, `StepsPerFlight` 계산값과 실제 스폰된 발판
개수가 일치하는지부터 확인한다.

### 17.3 증상 3 — 헤드룸 부족: 층수가 아니라 계단 배치의 문제일 가능성이 높다

**결론부터: 층을 늘릴 필요는 없어 보인다.** 이 프로젝트의 꺾음계단은 Flight A와 Flight B가
서로 다른 로컬 X에 위치해(완전히 같은 자리에 포개진 게 아니라 옆으로 나란히 배치됨) 있으므로,
"위층 발판이 아래층 발판 바로 위를 덮어서" 막히는 구조적 문제는 아닐 가능성이 크다. 그보다는
**계단참(landing)이 Flight A의 마지막 몇 단 위까지 뒤로 겹쳐서 내려와 있어서, 그 부분에서만
머리 높이가 눌리는 것**일 가능성이 높다 — 15.2절에서 예고했던 헤드룸 계산을 실제로 아직 안
해봤으니 나올 수 있는 결과다.

층고(`FloorHeight`)를 늘려서 이 문제를 풀려면, 대략적으로 계단참 부근 최소 헤드룸이
"`FloorHeight`/2 − 슬래브 두께" 수준까지 떨어질 수 있다는 걸 감안해야 한다 — 210cm 여유를
확보하려면 `FloorHeight`를 지금(300cm)의 1.5배 이상(대략 450cm 이상)으로 올려야 할 수도
있는데, 이건 주거용 층고로는 비현실적으로 높다. **따라서 층고를 올리는 방향은 권장하지
않는다.**

대신 다음 순서로 접근한다.

1. Flight A·Flight B의 **모든 단**에서, 바로 위쪽으로 가장 먼저 부딪히는 solid 지오메트리까지의
   실제 수직 거리를 하나하나 계산한다(추정하지 말고 직접 측정).
2. 210cm 미만인 지점이 정확히 어떤 요소(계단참? 반대쪽 Flight? 15장에서 만든 층 슬래브
   조각?) 때문인지 특정한다.
3. 그 요소 하나만 조정한다 — 대개는 계단참의 시작 위치를 Flight A의 마지막 단 좌표
   바로 다음(겹치지 않게)으로 다시 계산하는 것으로 해결된다(계단참이 Flight A의 런(run) 뒤쪽
   일부를 덮고 있었다면, 그 겹치는 부분만큼이 정확히 막힌 구간이 된다).
4. 이렇게 특정 요소를 고쳐도 210cm를 못 채우는 지점이 남는다면, 그때 가서 `FloorHeight`를
   조금(예: 300→330~350cm 정도) 올리는 걸 검토한다 — 처음부터 큰 폭으로 올리지 말고, 다른
   원인을 다 배제한 뒤 최소한만 조정한다.

### 17.4 실제 검증 결과 (위 추측 중 일부는 틀렸음 — 기록용)

Claude Code가 실측한 결과, 17.1~17.3절의 추측 중 정확했던 것과 틀렸던 것이 갈렸다. 다음
디버깅에서 같은 추측을 반복하지 않도록 결과를 남겨둔다.

- **17.1(코어 A/B 비대칭)은 틀렸다.** 코어 A·B 130개 포인트를 전부 대조한 결과 `ΔX=+4700`
  순수 평행이동으로 완전히 대칭이었고, 애초에 이 그래프에는 Filter/Boolean 노드 자체가
  없어서 "문 필터가 난간에 잘못 상속됐다"는 메커니즘이 성립할 수 없었다. 즉 코어 A/B는
  구조적으로 항상 동일했다 — 그 스크린샷의 좌우 비대칭은 코드 레벨 문제가 아니었다는 뜻이므로,
  같은 앵글로 양쪽을 다시 찍어 지금도 비대칭으로 보이는지부터 확인해야 한다(스테일 렌더링이나
  카메라 위치 차이였을 가능성이 있다).
- **17.2(계단실 내 미분류 공간)는 정확했다.** 다만 원인은 "일부가 아예 안 만들어짐"이 아니라
  **15장에서 만든 shaft void가 필요한 것보다 넓게 뚫려서, 계단이 지나가지 않는 안쪽 깊은
  영역(Y:384→800, 엘리베이터 쪽과 대칭되는 자리)까지 같이 비워버린 것**이었다. 1~4층, 코어
  A/B 양쪽에 그 자리 바닥을 다시 채워서 해결했다. 15.1절의 "필요한 만큼만 비운다"는 원칙을
  지금보다 더 좁게 해석했어야 했다는 교훈이 남는다.
- **17.3(헤드룸 부족)은 방향은 맞았지만 범인 지목은 틀렸다.** 계단참이 겹친 대상은 문서가
  추측한 Flight A가 아니라 **Flight B**였다(Flight A/B는 겹쳐 쌓인 게 아니라 나란히 배치돼
  있어서 Flight A 쪽은 원래부터 클리어런스에 문제가 없었다). `LandingDepth`를 150→80cm로
  줄이고 Flight A와 연결되는 쪽 모서리(Y=234)는 고정한 채 Flight B의 8개 발판과 바깥쪽
  난간을 그 값에서 다시 계산해서 해결했다 — 최소 헤드룸이 167.5cm에서 223.75cm로 개선됐다.
  "요소 하나만 조정하고 거기 종속된 걸 다시 계산한다"는 접근 자체는 그대로 유효했다.
- **부수 발견(미해결, 코스메틱):** 바깥쪽 난간이 프로젝트 전체에서 쓰는
  `ParapetHeight`=110cm가 아니라 층고 전체(300cm) 높이로 만들어져 있다. 기능적으로는
  문제없지만(오히려 추락 방지는 더 확실함) 시각적으로 다른 난간들과 일관성이 없다 — 여유
  있을 때 110cm로 맞추는 걸 다음 다듬기 작업으로 남겨둔다.

## 18. 17장 마무리: 난간 연결성은 정상 확인, 오버사이즈 슬릿 가드는 실제 헤드룸 버그였음

이번 장은 매번 스크린샷을 수동으로 주고받는 대신 **Cowork↔Claude Code 무인 루프**(로컬 스크립트가
Claude Code를 headless로 반복 호출하고, handoff/report 파일 쌍을 통해 Cowork 세션이 매 라운드
지시문을 쓰고 결과 데이터를 읽어들이는 방식)로 17장에서 남겨둔 두 항목을 마무리한 기록이다.
2라운드가 걸렸고, 둘 다 추측이 아니라 실측 데이터로 종결됐다.

### 18.1 최상단/최하단 층 난간 연결성 — 버그 아님으로 확정

1라운드는 강제 클린 리제너레이트(`ExecuteGraphInstance` + `GetNodeDataView`) 직후의 실제
포인트 데이터를 전부 뽑아 확인했다. 결과: 슬릿 가드 패널 20개(패널 2개 × 코어 2개 × 층 5개)가
전 층에서 바이트 단위로 동일하고, 인접 층끼리 완전히 맞물려(월드 Z 0~1500, 5개 층에 걸쳐) 이음매나
겹침이 전혀 없었다. `PCG_Apartment_Floor`/`PCG_Apartment_Stair` 어디에도 최상단/최하단 층만
다르게 잘라내는 층별 분기 로직 자체가 없다. 원본 스크린샷에서 옥상/1층 쪽이 "끊겨 보인" 건
애초에 그 위/아래로 이어질 대상이 없는 정상적인 건축적 종단부이고, 시각적으로 그렇게 보인 건
무채색 블록아웃 재질과 그 각도에서 최상층 계단을 가린 엘리베이터 코어 매스 때문일 가능성이 가장
높다.

2라운드에서 양쪽 코어를 가림 없이 정면으로 촬영한 클린 스크린샷(`dev/shot_coreA_clean.png`,
`dev/shot_coreB_clean.png`)으로 다시 시각 확인했다 — 코어 A·B 모두 지상부터 옥상까지 꺾음계단
실루엣이 끊김 없이 이어져 보이고, 예상대로 좌우 대칭이다. **이 항목은 그래프 수정이 전혀
필요 없었다 — 결함이 아니라 카메라 각도로 인한 착시였다.**

### 18.2 오버사이즈 슬릿 가드 패널: 코스메틱이 아니라 실제 Flight B 헤드룸 버그였음

17.4절은 바깥쪽 슬릿 가드 패널(층고 전체 300cm로 만들어져 `ParapetHeight`=110cm 규격을
벗어난 것)을 "미해결, 코스메틱"으로 기록하면서도, 기하학적 검토만으로는 실제로 이동을
막는지 확신할 수 없다고 남겨뒀다. 2라운드가 이 애매함을 해소했다.

- **적용한 수정**: `PCG_Apartment_Stair`의 `StairLocalTemplate` 안 슬릿 가드 패널 2개
  (seed 219/220)를 `z=150, scale.z=3`(0~300cm 범위)에서 `z=55, scale.z=1.1`(0~110cm =
  `ParapetHeight`, 자기 층 바닥에 딱 맞춰 앉음)로 수정했다 — 이제 6.4절의 세대 복도 파라펫과
  동일한 규격을 따른다. 재생성 후 실측 포인트 데이터로 확인한 결과, 20개 패널 전부가 양쪽
  코어에서 정확히 `floor_base ~ floor_base+110` 범위에 있었고, 그래프 애셋과 레벨 둘 다 저장까지
  완료해 에디터를 껐다 켜도 사라지지 않는 상태다.
- **원인을 정량적으로 확정**: 수정 전에는 패널의 0~300cm 전체 범위가 Flight B의 발판 구간
  (로컬 Z=150부터 시작)과 **모든 층에서** 겹치고 있었다 — 이게 바로 "매 층마다 똑같은 자리에서
  막힌다"는 원래 제보 증상의 정체였다. 수정 후 Flight B의 모든 발판과 정확히 Z-range를 대조한
  결과(`dev/check_overlap.py`), **겹침이 어디에도 남아 있지 않았고**, 가장 가까운 지점도
  계단참 전환부에서 9cm 여유가 있었다. Flight A는 애초에 패널의 바깥쪽 8cm 가장자리에만
  영향을 받아 중앙을 걷는 캐릭터와는 충분히 떨어져 있었으므로(17장 원래 계산 그대로) 이번
  수정과 무관하게 처음부터 문제가 없었다.
- **시각적으로도 확인**: 코어 A 내부, Flight B 계단참에서 위쪽 계단을 올려다보며 찍은
  `dev/shot_stair_interior.png`를 보면 발판이 시야 정면으로 끊김 없이 이어지고, 수정된 패널은
  보행 동선 바깥쪽의 평평한 측면 난간으로만 보인다.

**결론: ParapetHeight 수정은 단순한 정리 작업이 아니라, 매 층에서 재현되던 실제 Flight B
헤드룸 장애물을 고친 것이었다 — 정확한 기하학적 대조(겹침 0)와 수정 후 내부 스크린샷 둘 다로
확인됐다.** 이로써 17장에서 남았던 세 가지(비대칭 — 17.4절에서 착시로 판명, 미분류 계단실
공간 — 17.4절에서 수정 완료, 그리고 이번 헤드룸 버그)가 모두 종결됐다.

### 18.3 진행 방식 메모: 무인 루프가 잘 보여준 것

두 라운드 모두 13장 이후로 이어져 온 것과 같은 증거 원칙을 지켰다 — 스크린샷 외관만으로
판단하지 않고, 모든 결론을 실제 `GetNodeDataView` 포인트 데이터, 명시적 겹침 계산, 또는 알려진
좌표에서 목적을 갖고 찍은 스크린샷으로 뒷받침했다. 1라운드는 오버사이즈 패널이 실제로 이동을
막는지 추측하기를 명시적으로 거부하고, 그걸 확인하는 데 정확히 필요한 다음 단계를 제안했다 —
2라운드는 바로 그 후속 작업을 수행해서 검증된 답을 보고했다. 이게 이 루프의
`STATUS: CONTINUE`/`BLOCKED` 프로토콜이 의도한 실패 모드다 — 불확실성은 추측으로 덮지 않고
구체적인 다음 단계로 이월된다.

큐에 올라와 있는 다음 마일스톤 — 난간 바·창틀·에어컨 실외기 자리를 위한 임시 Cube 프리미티브
배치(나중에 실제 애셋으로 교체할 자리 표시)는 이번 수정 이후에도 **자동으로 시작하지 않는다** —
사람이 이번 라운드 결과를 먼저 검토한 뒤에 진행한다.

## 19. Phase 2: 난간 바·창틀·에어컨 실외기 임시 블록아웃

Phase 1의 구조적 버그가 모두 닫힌 뒤, 사용자가 큐에 있던 Phase 2 마일스톤 시작을 승인했다 —
재질/스타일 작업이 아니라 순수하게 자리 표시용 블록아웃을 추가하는 작업으로, 나중에 사용자가
각 자리를 실제 애셋으로 교체할 때 배치/크기를 다시 고민할 필요가 없게 하는 게 목적이다. 같은
무인 루프의 단일 라운드로 완료됐고, 엔진 기본 프리미티브(`/Engine/BasicShapes/Cube`, 기본
머티리얼)만 사용했다.

### 19.1 문서에 남아있던 오래된 메모 정정

작업 전에 라이브 그래프 구조부터 확인했는데, `UnitLocalTemplate`의 후면벽(복도 반대편, 세대의
외부 파사드)이 **이미** 0~90cm 하단벽과 210~300cm 상인방으로 나뉘어 있고, 그 사이에 실제로
120cm 높이의 창 개구부가 있는 상태였다. 이건 이 문서 자체의 6.5절/9장 메모("보류")와 모순되는데
— 아마 10장 파사드 디테일 작업 때 추가됐지만 문서 업데이트를 놓친 것으로 보인다. 나중에 다시
헷갈리지 않도록 여기 기록해둔다: **`PCG_Apartment_UnitRow`에는 이미 창 개구부가 존재**하므로,
거기에 트림과 실외기를 배치하는 건 배치 작업이었지 사람 판단이 필요한 설계 결정이 아니었다
(handoff에 넣어둔 "창 개구부가 아직 없으면 BLOCKED" 탈출구는 결국 쓸 필요가 없었다).

### 19.2 실제로 만든 것

- **난간 바**(항목 1): `ParapetHeight`=110cm 통짜 파라펫 블록(6.4절의 세대 복도 파라펫, 그리고
  18장에서 규격대로 고친 계단 슬릿 가드 패널 둘 다)을 얇은 세로 바 여러 개로 **교체**했다 —
  단면 4×4cm, 높이 110cm. 세대 복도 바는 세대 정면 폭 700cm에 걸쳐 20cm 간격으로 배치했고
  (세대당 35개), 인접 세대끼리 이음매에서 바가 겹치지 않도록 일부러 작은 간격을 남겼다. 계단
  바는 16cm 간격을 썼는데, 224cm 런(run)이 정확히 나눠떨어지도록 골라서(발판당 15개) 양 끝점이
  원래 패널의 가장자리와 정확히 일치한다. 통짜 블록 앞에 바를 겹쳐 세우는 대신 완전 교체를
  택한 이유는, 둘 다 남기면 콜리전이 중복되고 애초에 "속이 비치는 난간"을 만드는 목적에도
  어긋나기 때문이다. 이 작업엔 Loop Subgraph 우회 기법이 추가로 필요 없었다 — 바 목록을 실제
  좌표로 미리 계산해서 심는 방식은, 문/창 세그먼트 분할(6.3절, 10.1절)에서 이미 쓰던 기법
  그대로다.
- **창틀 트림**(항목 2): 세대당 5cm 두께 트림 Cube 4개를 기존 개구부 둘레(하단 Z=90, 상단
  Z=210, 좌우는 개구부 가장자리)를 따라 벽 바깥면에 맞춰 배치했다.
- **에어컨 실외기**(항목 3): 세대당 80×30×60cm Cube 1개를 창 하단 바로 아래, 외벽 바깥면에
  벽걸이 형태로 붙였다. 이 파사드가 건물 외피이지 걸어다니는 발코니가 아니라서 층마다 바닥이
  없으므로, 바닥에 세우는 대신 벽걸이로 처리했다.

## 20. Phase 3: 규모 조정·난간 단순화·계단 개방화·엘리베이터 코어·정문·층수 2배

사용자가 Phase 2 스크린샷을 직접 검토한 뒤 두 갈래 피드백을 줬다 — 기존 결과물 수정 4건과
완전히 새로운 구조 3건. 파라미터 자체(`UnitWidth`, `FloorHeight`)를 바꾸는 작업이 포함돼 있어서,
이후 모든 항목(문/창 세그먼트 폭, 난간 길이, 계단 단수 등)을 예전 공식 그대로 가져다 쓸 수
없고 라이브 그래프 값 기준으로 전부 다시 유도해야 했다. 여섯 개 마일스톤(3A~3F)으로 나눠
순서대로 처리했고, 마일스톤마다 재생성·포인트 데이터 검증·스크린샷·중간 보고를 거쳤다.

### 20.0 작업 시작 전 걸린 문제: 자동 루프 스크립트 버그 2건

Phase 3 핸드오프가 이전 라운드들보다 훨씬 길어지면서(약 10.5KB), `run-claude-loop.ps1`(v2)이
핸드오프 전체 내용을 `claude -p`의 커맨드라인 인자로 그대로 넘기는 방식의 한계에 걸렸다 —
`claude` CLI가 Windows에서 `.cmd` 셸을 거쳐 실행되면서 cmd.exe의 명령줄 길이 제한(약 8191자)에
걸려 핸드오프 본문이 중간에 잘렸고, Claude Code 스스로도 "핸드오프가 잘린 것 같다"고 응답을
남겼다. 게다가 이 라운드는 `claude-report.md`를 전혀 갱신하지 않았는데도, 스크립트가 그 파일에
남아있던 **이전 Phase 2의 낡은 "STATUS: COMPLETE"** 줄을 그대로 읽어 작업이 끝난 것으로 잘못
판단하고 루프를 멈춰버렸다.

두 버그 모두 스크립트를 고쳐서 해결했다(v3):

- **잘림 버그**: 핸드오프 전체를 인자로 넘기는 대신, "`dev/claude-handoff.md`를 직접 읽고
  그대로 수행하라"는 짧고 고정된 지시문만 넘기도록 바꿨다. Claude Code는 이미
  `--allowedTools`에 `Read`가 있으므로 핸드오프 파일을 스스로 읽을 수 있고, 이 방식은 핸드오프가
  앞으로 아무리 길어져도 커맨드라인 길이 제한에 걸리지 않는다.
- **낡은 리포트 오판 버그**: 라운드 시작 전 `claude-report.md`의 수정 시각을 기록해두고, 라운드가
  끝난 뒤 실제로 갱신됐는지 비교해서 갱신 안 됐으면 STATUS 줄을 신뢰하지 않고 루프를 멈추지
  않도록 고쳤다.

### 20.1 마일스톤 3A — 규모 조정 (`UnitWidth`×2, `FloorHeight`×1.5)

- `UnitWidth`: 700cm → **1400cm**. `FloorHeight`: 300cm → **450cm**.
- 작업 시작 전 `GetGraphStructure`로 네 그래프(`Main`/`Floor`/`UnitRow`/`Stair`)를 전부 확인한
  결과, **User Parameters로 노출된 값들이 실제로는 어디에도 연결돼 있지 않고, 모든 치수가
  `Create Points` 노드에 리터럴 좌표로 박혀 있다는 사실이 이번에 처음 드러났다**(`FloorOrigins`
  노드 코멘트에 "not yet wired"라고 명시돼 있었다). 즉 파라미터 슬라이더를 바꾸는 게 아니라,
  각 리터럴 좌표 뒤에 숨어있던 공식을 손으로 역산해서 새 값으로 다시 계산해 넣는 작업이었다.
- 기존에 문서화되지 않았던 관계식들을 이번에 처음 유도하고 검증했다(`dev/phase3_model.py`에
  정리): 코어 중심 오프셋(`UnitsPerSide*UnitWidth + CoreWidth/2`), 계단 앵커 X좌표(코어 중심
  기준 `±CoreWidth/4`), 세대-코어 경계벽 X좌표 등. 새 값을 계산에 넣기 전에 **이 공식들이
  기존(변경 전) 좌표를 정확히 재현하는지부터 검증**한 뒤에야 새 수치 계산에 사용했다.
- 창 개구부(하단 0~90cm, 개구부 90~210cm)는 `FloorHeight`에 비례하지 않는 **고정 절대 치수**로
  유지하고, 그 위 상인방만 새 층고(450cm)까지 늘렸다 — 실제 창문은 층고에 비례해서 커지지
  않는다는 판단.
- `StepsPerFlight = round((FloorHeight/2)/StairRiser)`를 새 층고 기준으로 재계산(225cm/flight),
  `StairRiser`=18.75cm를 그대로 유지해도 225/18.75=12로 정수가 딱 떨어져서 라이저 값 자체는
  건드릴 필요가 없었다.
- 검증: `ExecuteGraphInstance` 0메시지, 전체 포인트 수 **3233개**(공식 계산과 정확히 일치).
  스크린샷 `dev/shot_3a_rescale.png` — 창 간격이 눈에 띄게 넓어지고(구 700cm → 신 1400cm) 층
  높이도 눈에 띄게 커진 게 확인됨. Phase 1 헤드룸 수정은 `ParapetHeight` 기준이라 층고 변경에
  영향받지 않음을 재확인.

### 20.2 마일스톤 3B — 난간을 바 여러 개에서 런당 박스 1개로 단순화

Phase 2에서 만든 촘촘한 세로 바 여러 개(세대 복도 35개, 계단 15개)는 각 바가 나중에 넣을 실제
애셋 조각 하나씩을 대신하는 셈이었는데, 사용자가 실제로는 **런(run) 하나에 실제 애셋도
하나만 들어갈 것**이라고 결정했다. 그래서 각 런을 얇은 긴 박스 1개(두께 8cm, `ParapetHeight`
높이, 런 전체 길이)로 교체했다 — 세대 복도 런 1개당 1개, 계단 Flight 옆면 1개당 1개.

- 검증: 포인트 수가 3233개 → **743개**로 감소, 손으로 계산한 예상치와 정확히 일치(런당 바
  개수가 그대로 1개로 줄어든 것 외에는 아무것도 바뀌지 않았음을 확인).
- 스크린샷 비교: `dev/shot_3b_railbox_close2.png`(신규, 근접 촬영 — 세로 분할선 없는 매끈한
  판 하나로 보임) vs `dev/shot_corridor_railing_bars.png`(Phase 2, 같은 거리에서 촘촘한 세로
  줄무늬로 보임) — 육안으로도 "여러 개 → 1개" 전환이 명확히 대조된다.

### 20.3 마일스톤 3C — 계단 Y축 깊이를 건물 본체와 맞추고, 계단을 가리던 벽 제거

**깊이 불일치**: 건물 전체 Y깊이(`UnitDepth + CorridorWidth` = 980cm)에 비해 계단이 실제로
차지하는 Y범위는 3A 이후에도 겨우 416cm(약 42%)에 불과했다. 원인은 `LandingDepth`(17.4절에서
80cm로 줄여놨던 값)였다 — 계단 발판 폭(`StairTreadDepth×StepsPerFlight`=336cm)은 실제 계단
치수라 건드리지 않고, `LandingDepth`만 역산해서 **440cm**로 늘려 계단참 반대쪽 끝이 건물
뒷벽에서 14cm만 남기고 거의 맞닿도록 만들었다(0으로 딱 맞추지 않고 약간의 여유를 의도적으로
남김).

**계단을 가리던 벽**: `CoreLocalTemplate`의 모든 포인트를 계단 좌표계로 환산해서 겹침을
검사한 결과, seed 105 — 문 개구부가 전혀 없는 층고 전체 높이의 벽 패널 — 이 계단 통로 안에
그대로 남아있는 걸 발견했다(13.2절과 같은 종류의 "예전 좌표 잔재" 버그, 이번엔 실측으로 확인).
이 패널을 완전히 제거해서, 계단 쪽(코어 로컬 X 음수 방향)이 레퍼런스 사진처럼 완전히 개방되게
만들었다.

- 검증: 포인트 수 743 → **733개**(코어 2개 × 층 5개 = 10개 감소, 제거한 벽 포인트 수와 정확히
  일치). 스크린샷 `dev/shot_3c_stair_depth.png` — 꺾음계단과 훨씬 깊어진 계단참 슬래브가 건물
  본체 깊이만큼 뻗어있고, 계단 앞을 가리는 벽이 없어 구조적으로 완전히 개방된 형태로 보인다.
  다만 실제 재질/스타일링까지 레퍼런스 사진과 동일하게 만드는 건 이번 라운드 범위(엔진 기본
  프리미티브만 사용) 밖이라는 점은 리포트에 명시적으로 남겨뒀다.

### 20.4 마일스톤 3D — 건물 중앙에 전용 엘리베이터 코어 신설

건물 중앙(X=0)은 원래 안쪽 두 세대의 격벽이 맞닿는 자리라 여유 공간이 전혀 없었다 — 여기에
새 코어를 넣으려면 세대열을 바깥쪽으로 밀어야 한다. Claude Code는 이걸 "막힘(BLOCKED)"으로
보고할지 고민했지만, **세대열을 대칭으로 밀어내고 그에 따라 나머지 좌표를 다시 계산하는 건
3A에서 이미 했던 것과 같은 종류의 파라메트릭 재계산**이라 판단해서 막지 않고 기본값을 정해
진행한 뒤 근거를 리포트에 남겼다(사용자가 사전에 승인한 "전용 코어" 방식).

- 새 파라미터 `ElevatorCoreWidth`=300cm(엘리베이터 전용이라 계단이 있는 기존 코어(`CoreWidth`
  500cm)보다 좁게 설정) 추가. `CenterOffset`=150cm만큼 세대·코어·계단 앵커를 전부 바깥으로
  이동.
- 새 코어(`ElevatorCoreLocalTemplate`)를 만들 때 처음부터 계단 쪽과 같은 개방형으로 설계해서
  3C-2와 같은 벽 겹침 버그를 애초에 재현하지 않았다.
- 겹침 검사: 세대 안쪽 끝(150cm)과 엘리베이터 코어 경계(150cm)가 수치상 정확히 150.0=150.0으로
  맞닿아 틈도 겹침도 없음을 확인(육안이 아니라 산술로 검증).
- 검증: 포인트 수 733 → **763개**(신규 코어 관련 +30, 공식과 일치). 스크린샷
  `dev/shot_3d_elevcore.png` — 건물 중앙을 가로지르는 뚜렷한 수직 틈(하늘이 보임)이 파사드를
  둘로 나누고, 각 층 경계에 로비 슬래브 턱이 그 틈을 가로지르는 모습으로 신규 코어가 겹침 없이
  독립된 구조로 자리잡았음을 확인.

### 20.5 마일스톤 3E — 1층 건물 정문

3D에서 만든 엘리베이터 코어는 애초에 그 Y평면에 파라펫이 없어서, 건물 중앙에 이미
`ElevatorCoreWidth`(300cm)만큼의 틈이 나 있었다. 이 틈 안에 정문 개구부를 250cm(`DoorWidth`의
2.5배, handoff의 2~3배 권장 범위 안)로 잡아서 양옆 25cm씩 여유를 남겼다.

- `Main:MainGateGround`(기둥 2개 + 상인방)를 지상층(`FloorOrigins_Ground`)에만 스탬프.
- 상부층(1~4층)은 정문이 없지만 같은 틈이 그대로 뚫려 있으면 안전상 문제가 되므로, 세대 복도
  난간과 같은 스타일의 채움 난간(`Main:CenterRailingUpper`)을 상부층에만 추가로 스탬프 —
  handoff에 명시된 요구사항은 아니었지만 "지상층만 정문"이라는 지시를 따르려면 자연스럽게
  필요한 후속 조치였다.
- 검증: 포인트 수 763 → **770개**(정문 3개 + 상부 채움 난간 4개 = +7, 공식과 일치). 스크린샷
  `dev/shot_3e_gate.png` — 기둥+상인방 형태의 문틀이 뚜렷하고, 그 사이로 하늘이 보이는 개방된
  통로가 확인됨.

### 20.6 마일스톤 3F — 층수 2배 (`FloorCount` 5 → 10)

가장 구조적으로 안전한 변경이었다 — 나머지 마일스톤이 이미 파라메트릭하게 층마다 반복되도록
짜여 있어서, `Main:FloorOrigins`(10개 포인트)와 `Main:FloorOrigins_Upper`(9개 포인트)만
수정하면 됐다.

- 검증: 포인트 수 **1540개**, 손으로 유도한 전체 공식(`(13×6 + 5×2 + 1 + 1 + 27×2 + 5)×10 +
  (2 + 4×9 + 3 + 1×9) = 1490 + 50 = 1540`)과 정확히 일치. 최상층 위에 별도의 지붕 캡이 없는
  구조라 "계단 코어가 지붕에 부딪히는" 위험 자체가 존재하지 않음을 확인. 스크린샷
  `dev/shot_3f_full_elevation.png` — 10개 층 전체가 들어간 최종 입면.

### 20.7 최종 파라미터 값

| 파라미터 | 값 | 비고 |
|---|---|---|
| `UnitWidth` | 1400cm | 3A: 700cm에서 2배 |
| `FloorHeight` | 450cm | 3A: 300cm에서 1.5배 |
| `FloorCount` | 10 | 3F: 5에서 2배 |
| `LandingDepth` | 440cm | 3C: 80cm에서 재계산 |
| `StepsPerFlight` | 12 | 3A: 8에서 재계산 |
| `ElevatorCoreWidth`(신규) | 300cm | 3D |
| 정문 개구부 폭(그래프 파라미터 아님) | 250cm | 3E |

나머지 파라미터(`UnitsPerSide`, `CoreWidth`, `CorridorWidth`, `UnitDepth`, `DoorWidth`,
`WallThickness`, `ParapetHeight`, `StairRiser`)는 변경 없음. **다시 한번 강조**: 이 표의
값들은 그래프의 User Parameters에도 기록해뒀지만(문서화 목적), 실제 지오메트리는 여전히 각
`Create Points` 노드에 리터럴 좌표로 박혀 있어서 파라미터 슬라이더만 바꿔서는 반영되지
않는다 — 다음에 이 치수들을 또 바꿔야 한다면 `dev/phase3_model.py`의 검증된 공식을 재사용해서
같은 방식(라이브 값 확인 → 공식으로 역산 → `UpdateNode`)으로 진행해야 한다.

### 20.8 다음 단계

여섯 마일스톤 모두 완료·검증·저장까지 끝났고, handoff의 완료 규칙에 따라 이후 다른 작업을
자동으로 이어가지 않았다. 레퍼런스 사진과의 완전한 재질/스타일 일치, 실제 엘리베이터 카/도어
애셋, 정문 실제 스타일링은 모두 이번 라운드 범위(프리미티브 전용) 밖으로 남겨뒀다 — 사용자가
에디터에서 직접 확인한 뒤 다음 방향을 정하는 수동 단계다.

## 21. Phase 4: 계단·바닥 버그 6건 수정 + 정면 창(BP_Glass) 신설 + 문 상부 마감

사용자가 Phase 3 결과물을 에디터에서 직접 둘러보고 스크린샷 8장에 빨간 펜으로 표시해서 보내준
피드백이다 — 기존 결과물 버그 6건과 신규 추가 2건. 애매한 지점(현관문 이동 기준점, 창 재배치
방향, 문 상부 마감 방식) 세 곳은 작업 시작 전에 AskUserQuestion으로 먼저 확정한 뒤 핸드오프에
반영했다. 여덟 개 마일스톤(4A~4H)을 순서대로 처리했고, 이번에도 자동 루프 **한 라운드**로
전부 끝났다(약 35분, $15.03).

### 21.1 마일스톤 4A — 양쪽 계단 코어에 복도 난간이 아예 없었음

라이브 데이터로 확인한 결과, 세대 자체의 난간(3B)은 세대-코어 경계에서 정확히 멈추도록 만들어져
있었지만, **코어(계단실) 구간 500cm 폭 전체에는 애초에 난간이 하나도 없었다** — "끊겨 보인다"는
피드백의 정체가 이거였다. `CoreLocalTemplate`에 코어 폭 전체를 가로지르는 난간 박스를 하나
추가해서 양쪽 코어·전 층에 한 번에 적용했다. 추가로 상부층의 계단 통로 앞 복도 바닥에도 빈
구간이 있어서 `CoreVoidCorridorFill_Upper`를 새로 만들어 메웠다(지상층은 기존
`StairwellSlab_Ground`가 이미 덮고 있어 불필요). 포인트 수 1540→1578, 공식과 정확히 일치.

### 21.2 마일스톤 4B — 계단 뒷면(Flight A)에 착지 바닥이 없었음

`Main:StairwellSlab_Upper`의 기존 "도착 계단참" 패치가 Flight B 쪽에만 있고 Flight A 쪽에는
전혀 없다는 걸 좌표 대조로 확인했다 — 정확히 사용자가 지적한 "앞은 있는데 뒤는 없어서 불안정"
증상. 같은 모양의 패치를 Flight A 쪽에도 대칭으로 추가했다. 포인트 수 1578→1596.

### 21.3 마일스톤 4C — 복도 폭 1.5배 확장

`CorridorWidth` 180→270cm. 이 값에 의존하는 모든 노드(세대 바닥/난간, 양쪽 코어 로비 슬래브,
엘리베이터 코어 로비 슬래브, 정문/채움 난간, 4A에서 새로 만든 상부층 바닥 채움까지)를 전부
재계산했다. 17장에서 계단 깊이를 맞출 때 썼던 "건물 전체 Y깊이" 기준값(980cm)이 이제
1070cm(800+270)로 바뀌어서 비율이 살짝 달라졌다는 점은 handoff 지시대로 기록만 해두고, 계단
자체 치수는 안 건드렸으므로 추가 조치는 하지 않았다. 포인트 수는 변화 없음(1596, 위치만 이동).

### 21.4 마일스톤 4D — 각 세대 현관문을 세대 자체 중심에서 30% 이동

AskUserQuestion으로 "중심"이 건물 전체 중심이 아니라 **각 세대 자체 정면 폭의 중심**이라는 걸
먼저 확정했다. 오프셋 = `0.3 × (UnitWidth/2 − DoorWidth/2)` = 195cm. 세대 템플릿이 좌우 미러링
되는 구조라, 템플릿 로컬 좌표계에서 한쪽 방향으로만 오프셋을 줘도 양쪽 세대 모두 "건물 중심에서
먼 쪽(=각자 가까운 코어 쪽)"으로 일관되게 이동하는 걸 대수적으로 확인한 뒤 결정했다(반대 방향도
구조적으로는 동등하게 유효했지만, 이 방향이 "각 세대가 자기와 가까운 코어 쪽으로 출입한다"는
느낌이 더 자연스러워서 선택). 문 양옆 벽 세그먼트를 새 위치 기준으로 재계산(845cm/455cm) —
둘 다 문 폭보다 훨씬 넓어서 옆 벽과 안 부딪히는 것도 확인. 포인트 수 변화 없음(1596).

### 21.5 마일스톤 4E — 엘리베이터 코어 1층 바닥 누락

조사해보니 엘리베이터 코어의 로비 쪽 슬래브 자체는 매 층 정상적으로 있었다 — 문제는 계단
코어들이 지상층에서만 예외적으로 받는 "전체 채움 슬래브"(`StairwellSlab_Ground`, 계단실 개구부
쪽을 지상층에만 막아주는 처리)에 해당하는 게 엘리베이터 코어에는 없었다는 것. 엘리베이터
샤프트 쪽은 원래 매 층 뚫려있어야 하는 설계(3D)라 계단 코어와 완전히 같은 방식은 아니지만,
지상층만큼은 막아주는 예외가 빠져 있었다. `Main:ElevatorCoreSlab_Ground`를 새로 추가해서
해결. 포인트 수 1596→1597.

### 21.6 마일스톤 4F — 후면 창을 천장 근처로 재배치

AskUserQuestion으로 "천장 근처로 창을 올리는 것"이 맞다는 걸 확정한 뒤 진행. 기존 하단
0~90cm/개구부 90~210cm였던 창을 **하단 305cm/상단 425cm**로 옮겼다(개구부 높이 120cm는 유지,
천장 450cm에서 25cm만 남기고 거의 붙임). 창틀 트림 4개, 세로 트림 바 2개, 실외기(35cm 아래
간격 유지, z=270으로 이동)까지 전부 새 위치를 따라가도록 재계산했다. 이번 변경은 4G의 신규
정면 창에는 적용하지 않는다(둘은 별개 디자인). 포인트 수 변화 없음(1597).

### 21.7 마일스톤 4G — 신규: 정면(복도측) 창 2개 추가, 실제 BP_Glass 애셋 사용

이번 프로젝트에서 처음으로 Cube 플레이스홀더가 아니라 **실제 애셋(`BP_Glass`)을 그대로
스폰**했다. 먼저 `BP_Glass`가 뭔지부터 실측 확인했다 — `BP_Breakable_Base`를 상속한 액터로
`GeometryCollectionComponent`를 가지고 있어서(단순 스태틱 메시가 아님), Static Mesh Spawner가
아니라 PCG의 **Spawn Actor** 노드가 필요했다. 임시로 레벨에 하나 스폰해서 콜리전 박스 크기(약
192×8×160cm)를 실측한 뒤 지웠고, 이 실측값으로 개구부에 맞는 스케일을 계산했다. 개구부는
150×120cm(4F의 재배치 방식이 아니라 원래의 중앙 정렬 방식 재사용, 4F는 이 신규 창에는 적용
안 함), 세대당 2개(x=-350, x=+400, 4D에서 옮긴 문 위치와 안 겹치는 것까지 확인). 검증:
`Main:SpawnFrontWindowGlass`에서 포인트 120개(세대6×층10×창2), `find_actors`로 실제 레벨에
`BP_Glass_C` 액터 120개가 스폰된 것까지 확인. 전체 블록아웃 포인트 수 1597→1957.

### 21.8 마일스톤 4H — 문 상부 마감

AskUserQuestion으로 "창문과 같은 방식(문 높이까지만 개방, 그 위는 벽)"이 맞다는 걸 확정한 뒤
진행. 문 개구부를 210cm에서 잘라내고 그 위 210~450cm 구간을 상인방+벽으로 막았다 — 4D에서
이동한 새 문 위치를 기준으로 계산했으므로(4D 다음에 처리하도록 handoff에 명시) 옛 중앙 위치가
아니라 실제 현재 위치에 맞게 마감됐다. 포인트 수 1957→2017.

### 21.9 결과 확인

여덟 마일스톤 모두 `ExecuteGraphInstance` 0메시지로 재생성됐고, 포인트 수는 매 단계 손으로
유도한 공식과 정확히 일치했다. 스크린샷으로 직접 확인한 것: 코어 난간이 세대 난간과 끊김 없이
이어짐(4A), 문 상부가 창과 같은 방식으로 막히고 양옆에 실제 유리 액터가 보임(4H), 복도 폭이
넓어지고 각 층 창이 천장 쪽에 규칙적으로 배치된 넓은 입면(4C). 그래프 애셋 4개와 레벨 모두
저장 완료(`is_dirty` false). handoff의 완료 규칙대로 이후 작업은 자동으로 이어가지 않았다.
